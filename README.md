# Carbone Reports

Генерация отчётов на базе Carbone с редактированием шаблонов в браузере (OnlyOffice) и интерфейсом на GravityUI.

[![CI](https://github.com/SamRozhkov/carbone-report/actions/workflows/ci.yml/badge.svg)](https://github.com/SamRozhkov/carbone-report/actions/workflows/ci.yml)

Спецификация: `docs/superpowers/specs/2026-10-02-carbone-reports-design.md`.

## Разработка API

Требования: Node 22 (`nvm use`), pnpm 10 (`corepack enable`), запущенный Docker (для интеграционных тестов).

```bash
pnpm install
pnpm test          # юнит-тесты
pnpm test:int      # интеграционные (PostgreSQL, Redis и SeaweedFS в testcontainers; затем выбранные файлы на S3 — test:int:s3)
pnpm typecheck && pnpm lint
```

Локальный запуск API:

```bash
docker run -d --name cr-pg -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=app -p 5432:5432 postgres:17-alpine
cp .env.example .env   # заполнить секреты
cd apps/api && node --env-file=../../.env --import tsx src/server.ts
```

## Запуск в Docker

Нужен Docker с Compose v2.24+. Первый запуск скачивает образы OnlyOffice и Carbone (несколько ГБ).

```bash
cp .env.example .env      # заполнить обязательные переменные
```

**Разработка** (API с hot reload, интерфейс на http://localhost:8080, API напрямую на :3000, PostgreSQL на :55433; порты 8080, 3000 и 55433 слушают только 127.0.0.1):

```bash
pnpm stack:dev
```

**Прод** (HTTPS в nginx; положите сертификат и ключ в `certs/fullchain.pem` и `certs/privkey.pem`;
для локальной проверки — `./scripts/dev-cert.sh`):

```bash
pnpm stack:prod
```

Редирект с HTTP на HTTPS ведёт на стандартный порт 443; если `WEB_HTTPS_PORT` другой, открывайте `https://host:<порт>` напрямую.

**Проверка работающего стека** (сначала `pnpm install` на хосте):

```bash
pnpm stack:smoke                                        # разработка, http://localhost:8080
BASE_URL=https://localhost pnpm stack:smoke --insecure  # прод с самоподписанным сертификатом
```

Если `WEB_HTTPS_PORT` не 443, укажите порт в `BASE_URL`, например `BASE_URL=https://localhost:8443`.

Остановить: `pnpm stack:down` (данные сохраняются в томах; `docker compose down -v` удалит их).

Наружу в проде открыт только nginx. Маршруты `/internal/*` закрыты: их вызывает только OnlyOffice внутри сети.
Режимы разработки и прода на одном хосте используют один проект compose, а значит общие тома `pgdata` и `s3_data`. Образ разработки называется `carbone-reports-api:dev` и не затирает прод-образ.

### Данные

Состояние хранится в томах `pgdata` (PostgreSQL) и `s3_data` (SeaweedFS: файлы шаблонов и отчётов в бакете `S3_BUCKET`, по умолчанию `carbone-reports`). Тома `carbone_templates` и `oo_*` восстанавливаются сами. Резервные копии — в разделе [«Резервное копирование»](#резервное-копирование).

`POSTGRES_PASSWORD` применяется только при первом создании тома `pgdata`; позже пароль меняется внутри PostgreSQL (`ALTER USER`), а не в `.env`.

### Файлы в S3-хранилище

API хранит файлы в S3-совместимом хранилище: в compose это сервис `s3` — [SeaweedFS](https://github.com/seaweedfs/seaweedfs), официальный образ `chrislusf/seaweedfs` с закреплённой версией, все компоненты в одном контейнере (`weed mini`), данные в томе `s3_data`. Сервис работает только во внутренней сети `s3` вместе с `api` и `backup`: порты и веб-интерфейсы наружу не публикуются, включён только S3 (порт 8333). Поэтому несколько экземпляров API могут работать без общего тома.

Переменные в `.env`:

- `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` — обязательны (без них compose не запустится), например `openssl rand -hex 16` и `openssl rand -hex 32`; допустимы латинские буквы, цифры и `. _ ~ + / = -`. При каждом старте сервис `s3` создаёт из них единственную учётную запись S3 (`docker/s3/entrypoint.sh`, файл внутри контейнера); её же используют `api` и `backup`. Чтобы сменить ключи, поменяйте их в `.env` и выполните `docker compose up -d s3 api backup` (иначе агент бэкапа продолжит работать со старыми ключами). Данные не меняются;
- `S3_BUCKET` — имя бакета, по умолчанию `carbone-reports`. API создаёт бакет при первом старте (`S3_CREATE_BUCKET=true` в compose); сам SeaweedFS бакеты при записи не создаёт. Бакет должен принадлежать одной установке: восстановление выполняет `rclone sync` и удаляет из бакета все объекты, которых нет в архиве (в том числе чужие), а блокировка, которая согласует бэкап с удалением файлов, действует только в базе этой установки и другие установки с тем же бакетом не остановит.

Сервис `s3` монтирует `docker/s3/entrypoint.sh` из каталога проекта, поэтому `docker compose` запускается из корня репозитория.

**Перенос установки с тома `storage`** (обновление с версии до Плана 14) — через бэкап и восстановление, формат архива одинаков:

1. До обновления сделайте ручной бэкап старой версией: `docker compose --profile backup run --rm backup now`.
2. Добавьте в `.env` `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`, обновите код и поднимите стек: API создаст пустой бакет.
3. Восстановите копию: `scripts/restore.sh backups/<каталог>` — база заменится той же, а файлы из архива окажутся в бакете. Восстановление заменяет базу целиком и очищает Redis: изменения, сделанные после бэкапа из шага 1 (новые шаблоны, отчёты, пользователи), будут потеряны, поэтому между шагами 1 и 3 с системой не работают.
4. Проверьте, что шаблоны открываются и отчёты скачиваются. Том `storage` больше не используется; удалить его можно вручную: `docker volume rm carbone-reports_storage`.

### Redis

Сервис `redis` (`redis:7-alpine`, без сохранения на диск, `maxmemory 128mb`) хранит общее для всех экземпляров API временное состояние:

- кэш шаблонов Carbone (`cr:carbone:tpl:<id>`, срок жизни 7 дней) — шаблон не загружается в Carbone заново при каждом отчёте;
- счётчики ограничения попыток входа (`cr:rl:*` — по логину, `cr:rl-ip:*` — по IP; см. [Ограничение попыток входа](#ограничение-попыток-входа));
- флаг обслуживания `cr:maintenance` на время восстановления из бэкапа (его ставит и снимает агент бэкапа, см. [Бэкапы в админке](#бэкапы-в-админке)).

Бэкапить Redis не нужно: после перезапуска он пуст, и всё восстанавливается само. Адрес задаёт `REDIS_URL` (по умолчанию `redis://redis:6379`); в compose он собирается с паролем: `redis://:${REDIS_PASSWORD}@redis:6379`.

Redis требует пароль (`--requirepass`). Переменная `REDIS_PASSWORD` в `.env` обязательна (только hex: `openssl rand -hex 32`), без неё `docker compose` не запускается. Пароль проверяется при старте контейнера `redis`. Если в нём есть что-то кроме `0-9a-f`/`A-F`, контейнер завершается с сообщением «REDIS_PASSWORD: только шестнадцатеричные символы (openssl rand -hex 32)» (видно в `docker compose logs redis`), а `api` не запускается. Пароль подставляется внутри контейнера и не виден в команде (`docker inspect`), но есть в его окружении. `redis-cli` внутри контейнера берёт пароль из `REDISCLI_AUTH`, поэтому healthcheck и `docker compose exec -T redis redis-cli …` работают без `-a`. Чтобы сменить пароль, поменяйте `REDIS_PASSWORD` в `.env` и выполните `docker compose up -d redis api backup` (агент бэкапа тоже подключается к Redis с паролем; данные Redis одноразовые).

Redis подключён только к внутренней сети `cache` (`internal: true`), общей с `api` и агентом бэкапа (сервис `backup`). Другие сервисы (nginx, OnlyOffice, Carbone, демо-БД) его не видят, и выхода наружу у этой сети нет.

В compose `api` при старте ждёт, пока Redis станет healthy (`depends_on`). Работа без Redis относится ко времени после запуска. Если Redis стал недоступен, API продолжает работать: кэш считается промахом (шаблон каждый раз загружается в Carbone, отчёты формируются чуть медленнее), а ограничение попыток входа считается в памяти каждого экземпляра API, пока Redis не вернётся. В журнале API появляются ошибки подключения (не чаще раза в 30 с).

### Ограничение попыток входа

Вход (`POST /api/auth/login`) ограничен двумя независимыми лимитами; срабатывает тот, что исчерпан первым, ответ — `429 TOO_MANY_ATTEMPTS`:

- **по логину** — 10 попыток в минуту на логин (без учёта регистра), «слишком много попыток входа, повторите через минуту»;
- **по IP** — 30 попыток в минуту с одного адреса при любых логинах, «слишком много попыток входа с этого адреса, повторите через минуту».

Счётчики лежат в Redis и общие для всех экземпляров API. Если Redis недоступен или отвечает ошибкой, лимиты продолжают действовать, но считаются в памяти каждого экземпляра API отдельно (при N экземплярах — до N × лимит попыток). После ошибки API 5 с не обращается к Redis, затем пробует снова; в журнале — «Redis недоступен — лимиты запросов считаются в памяти экземпляра» (не чаще раза за 5 с).

IP клиента API берёт из `X-Forwarded-For`, который дописывает nginx: доверяется ровно одному прокси (`TRUSTED_PROXY_HOPS = 1` в `apps/api/src/app.ts`, аналог `trustProxy: 1`), так что адреса, подставленные клиентом в заголовок, не учитываются. В Fastify 5 число в `trustProxy` не доверяет ни одному хопу (fail-closed): все клиенты получили бы адрес nginx и делили один общий лимит входа 30 в минуту на весь сайт. Поэтому доверие задано функцией `trustProxyHops()`. Если перед nginx стоит ещё один прокси или балансировщик, все клиенты получат его адрес и разделят один лимит — увеличьте `TRUSTED_PROXY_HOPS`, а не `trustProxy`; это изменение кода, а не настройка. Пользователи за общим NAT или корпоративным прокси тоже делят лимит по IP. Если исходный адрес клиента теряется, все клиенты делят один лимит по IP: например, при публикации портов в Docker Desktop/OrbStack (адрес шлюза хоста) или IPv6 через docker-proxy; один злоумышленник тогда может на минуту исчерпать попытки входа для всех. Если это важно, поставьте nginx в сеть хоста или используйте прокси, сохраняющий исходный адрес. Остаточный риск: код внутри контейнера, который достаёт до `api:3000` напрямую (в сети compose по умолчанию или через опубликованный в dev 127.0.0.1:3000), может подделать `X-Forwarded-For` и обойти только лимит по IP; лимит по логину это не затрагивает.

### Запуск из готовых образов

CI публикует образы после зелёных проверок:

- `ghcr.io/samrozhkov/carbone-report-api`, `ghcr.io/samrozhkov/carbone-report-web`;
- `ghcr.io/samrozhkov/carbone-report-backup` (сервис `backup`: агент бэкапа на Node поверх `postgres:17-alpine` + `rclone`);
- теги: `latest` и `main` — последняя сборка `main`, `sha-<коммит>`, `X.Y.Z` и `X.Y` — релизы по тегам `vX.Y.Z`.

```bash
# в .env
API_IMAGE=ghcr.io/samrozhkov/carbone-report-api:1.0.0
WEB_IMAGE=ghcr.io/samrozhkov/carbone-report-web:1.0.0
BACKUP_IMAGE=ghcr.io/samrozhkov/carbone-report-backup:1.0.0

docker compose pull api web s3 backup
docker compose up -d --no-build
```

С заданными `API_IMAGE`/`WEB_IMAGE` не используйте `pnpm stack:*`: они пересобирают локальные исходники и тегируют их под имя релиза. Применяйте `docker compose pull` и `up -d --no-build`.

Новые пакеты GHCR приватные: сделайте их публичными (Package settings → Change visibility) или войдите на сервере: `echo <token> | docker login ghcr.io -u <user> --password-stdin` (токен с правом `read:packages`).

### Обновление / выкат

Добавьте `REDIS_PASSWORD` в `.env` перед обновлением (`openssl rand -hex 32`, см. [Redis](#redis)): без неё `docker compose` не запустится.

Добавьте `BACKUP_AGENT_TOKEN` в `.env` перед обновлением до версии с управлением бэкапами из админки (`openssl rand -hex 32`, не короче 32 символов): без него `docker compose` не запустится — ни `up`, ни `run`, ни `scripts/restore.sh`. Сервис `backup` теперь запускается вместе со стеком (`docker compose up -d`), профиль `backup` больше не нужен.

Перед обновлением сделайте [ручной бэкап](#резервное-копирование) (кнопка «Сделать бэкап» в админке или `docker compose run --rm backup now`): миграции выполняются при старте API, а миграция 0002 удаляет колонку `ssl`, поэтому откат возможен только восстановлением из копии. После этого обновления каждому пользователю один раз нужно войти заново.
`stack:smoke --carbone-restart` разрушителен (пересоздаёт carbone и удаляет том с кэшем шаблонов) и предназначен только для стендов разработки; даже на проде через localhost это даёт около 40 с простоя Carbone.

Сессионная cookie в проде помечена `Secure`, поэтому интерфейс работает только по HTTPS.

### Резервное копирование

**Что входит в бэкап:** база `app` (`pg_dump -Fc`) и файлы шаблонов и отчётов — бакет в сервисе `s3`. Сервис `backup` копирует бакет через `rclone` (провайдер `SeaweedFS`) во временный каталог и упаковывает его в `storage.tar.gz` того же формата, что раньше давал том `storage`; временный каталог затем удаляется. Дамп и копия бакета снимаются под одной блокировкой, поэтому они согласованы: пока идёт бэкап, API откладывает удаление файлов.

Сервис `backup` — агент бэкапа (`apps/backup-agent`, Node). Он запускается вместе со стеком, выполняет бэкап по расписанию и бэкапы и восстановление из админки ([Бэкапы в админке](#бэкапы-в-админке)) и вызывает те же скрипты `docker/backup/*.sh`. Образ собирается из `docker/backup/Dockerfile` с контекстом — корнем репозитория: `postgres:17-alpine`, `rclone`, Node, агент, скрипты и миграции `apps/api/drizzle` (по ним агент проверяет версию схемы бэкапа). Правка скриптов требует пересборки: `docker compose build backup`. Настройки S3 передаются `rclone` переменными окружения (`RCLONE_CONFIG_S3_*`), файла конфигурации с ключами нет.

**Что не входит:**

- `.env` с `ENCRYPTION_KEY`: без него пароли источников данных из бэкапа не расшифровать;
- `certs/`;
- кэши OnlyOffice и Carbone (тома `oo_*` и `carbone_templates` восстанавливаются сами).

Храните `.env` и `certs/` отдельно и надёжно.

Каждый бэкап — каталог `backups/<ГГГГ-ММ-ДДTЧЧ-ММ-ССZ>/` (или в вашем `BACKUP_DIR`; время UTC) с файлами `db.dump`, `storage.tar.gz` и `manifest.txt` (размеры и sha256). Незавершённый бэкап остаётся с суффиксом `.partial` и не участвует в ротации. Бэкапы перед восстановлением называются `pre-restore-<время>`: `BACKUP_KEEP` на них не действует (и сам такой бэкап обычные копии не ротирует), хранятся 3 последних; бэкап, из которого сейчас восстанавливают, ротацией не удаляется. В `backups/.op/` агент хранит состояние (`state.json`), замок `.op.lock` и журналы 20 последних операций. Ротация (удаление копий сверх `BACKUP_KEEP`) выполняется только после успешного обычного бэкапа, поэтому серия неудачных запусков не удаляет старые исправные копии. Каталоги `.partial` сами не удаляются: выясните причину сбоя по журналу и удалите их вручную, например `rm -rf backups/*.partial` (когда бэкап не идёт).

**По расписанию** бэкап запускает сам агент — сервис `backup` поднимается вместе со стеком (`docker compose up -d`). Если в момент запуска идёт другая операция (бэкап или восстановление из админки, ручной `now`), запуск по расписанию пропускается с записью в журнале.

Переменные в `.env`:

- `BACKUP_AGENT_TOKEN` — обязательный токен между `api` и агентом (не короче 32 символов, `openssl rand -hex 32`); без него `docker compose` не запускается;
- `BACKUP_CRON` — расписание в формате cron, по умолчанию `0 3 * * *`. Время берётся в часовом поясе `TZ` (по умолчанию `Europe/Moscow`), а не в UTC. Строка должна состоять ровно из 5 полей; иначе контейнер завершается с кодом 2 и сообщением «BACKUP_CRON: ожидается 5 полей cron» в журнале (и из-за `restart: unless-stopped` перезапускается с той же ошибкой, пока строку не исправят). Неверное значение поля или часовой пояс — «BACKUP_CRON: неверное выражение … или часовой пояс TZ=…»;
- `BACKUP_KEEP` — сколько последних копий хранить, по умолчанию 14;
- `BACKUP_TIMEOUT` — предельное время каждого шага (`pg_dump` и архивации файлов): целое число секунд ≥ 1 без суффиксов (`3600`, а не `1h` или `60m`), по умолчанию 3600. Неверное значение проверяется при старте контейнера: он завершается с кодом 2 и сообщением «BACKUP_TIMEOUT должен быть целым числом секунд ≥1». Шаг, не уложившийся в срок, получает TERM (а через 60 с — KILL) и прерывается, копия остаётся `.partial`, а блокировка снимается — зависший бэкап не задерживает удаление файлов в API бесконечно;
- `BACKUP_DIR` — каталог на хосте, по умолчанию `./backups`.

Журнал: `docker compose logs backup`.

**Вручную**, например перед выкатом:

```bash
docker compose run --rm backup now
```

Ручной бэкап и агент не работают одновременно: если агент занят, команда завершается с кодом 75 и сообщением «идёт другая операция с бэкапами (агент) — повторите позже». Пока агент в состоянии «требуется восстановление» (см. ниже), ручной бэкап сохранил бы частично заменённую базу — сначала завершите восстановление.

**Аварийное восстановление** (без веб-интерфейса; обычно восстановление запускается из админки):

```bash
scripts/restore.sh backups/<каталог>
```

Скрипт:

1. сверяет sha256 файлов с `manifest.txt`;
2. просит ввести `restore` для подтверждения;
3. останавливает агент бэкапа (сервис `backup`): он не начнёт бэкап посреди замены файлов и не вернёт флаг обслуживания;
4. останавливает `api` и `web` (интерфейс недоступен до конца восстановления);
5. заменяет базу `app` дампом в одной транзакции: удаляет схемы `public` и `drizzle` целиком и создаёт их заново из дампа (при ошибке база остаётся прежней);
6. заменяет файлы хранилища архивом (архив проверяется до изменений): распаковывает его во временный каталог и выполняет `rclone sync` в бакет — объекты, которых нет в архиве, удаляются. Архив распаковывается в `/tmp` одноразового контейнера `backup`, поэтому Docker нужно свободное место примерно размером с распакованный архив (данные в бакете, а не сжатый `storage.tar.gz`). `STORAGE_BACKEND=local scripts/restore.sh …` восстанавливает том `storage` — только для установок, где сам API работает в режиме local (`STORAGE_BACKEND=local` у сервиса `api`); стек из этого репозитория работает с S3, и скрипт в режиме local для него откажется работать;
7. отмечает в `backups/.op/state.json` незавершённое восстановление из админки как `failed (resolved externally)`: после запуска агент больше не включает режим обслуживания;
8. очищает Redis (`FLUSHALL`; если Redis остановлен — сначала запускает его): кэш шаблонов Carbone после замены базы устарел бы, и отчёт мог бы молча сформироваться по прежнему шаблону. Счётчики попыток входа тоже сбрасываются. Если очистить не удалось, скрипт предупреждает и продолжает — тогда выполните `docker compose exec -T redis redis-cli FLUSHALL` вручную;
9. запускает `api` и `web`, затем снова `backup`.

Если шаг после остановки `api` и `web` завершился ошибкой, скрипт сообщает, успела ли замениться база, снова запускает `backup` и оставляет `api` и `web` остановленными: устраните причину и запустите скрипт снова или верните стек командой `docker compose up -d --wait api web` (если база уже заменена, а Redis не очищен, скрипт напомнит сначала очистить его).

Восстанавливать можно и в чистый стек: сначала поднимите его с тем же `.env`, затем запустите скрипт. Можно восстанавливать и в более новую версию приложения: база полностью заменяется состоянием из бэкапа (таблицы и миграции, которых в дампе нет, удаляются), а API при старте заново применит недостающие миграции.

**Копия на другой сервер** остаётся за администратором, например по cron на хосте:

```bash
rsync -a --exclude '*.partial' backups/ backup-host:/srv/carbone-reports-backups/
```

Здесь `backups/` — каталог по умолчанию (или ваш `BACKUP_DIR`). Ротацию копий на удалённой стороне настраивает администратор.

### Бэкапы в админке

Пункт «Бэкапы» в меню администратора появляется, когда у `api` заданы `BACKUP_AGENT_URL` и `BACKUP_AGENT_TOKEN` (в compose — всегда). Агент слушает порт 8080 только во внутренней сети `backup` между `api` и `backup`: внутри стека он доступен по адресу `http://backup-agent:8080` (псевдоним `backup-agent` есть только в этой сети), наружу порт не публикуется, каждый запрос к нему, кроме `/health`, требует токен. `BACKUP_AGENT_TOKEN` обязателен в `.env` для любой команды `docker compose`, в том числе для `scripts/restore.sh`; при обновлении добавьте `BACKUP_AGENT_TOKEN` в `.env`: `openssl rand -hex 32`.

- **Список** — дата, имя каталога, тип (обычный или «перед восстановлением»), размер базы и файлов, последняя миграция, статус. Незавершённые (`.partial`) восстановить нельзя.
- **«Сделать бэкап»** — то же, что `docker compose run --rm backup now`. Над таблицей — последняя операция: кто запустил, этап, статус и журнал.
- **«Восстановить»** — после ввода имени бэкапа:
  1. проверка: контрольные суммы и версия схемы. Бэкап, сделанный более новой версией приложения, не восстанавливается;
  2. бэкап текущего состояния (`pre-restore-<время>`);
  3. режим обслуживания: все пользователи видят экран «Идёт восстановление из бэкапа…», API отвечает `503`;
  4. замена базы одной транзакцией, миграции до текущей схемы;
  5. восстановление файлов в бакете (`rclone sync`);
  6. очистка Redis.

  По окончании страница перезагрузится. Пользователь и версия его сессий берутся из восстановленной базы, поэтому может понадобиться войти заново, в том числе администратору.

- **Если восстановление упало после замены базы**, режим обслуживания остаётся. Агент печатает одноразовый код в журнал: `docker compose logs backup | grep 'КОД ВОССТАНОВЛЕНИЯ'`. На экране обслуживания введите код из журнала (регистр букв, пробелы и дефисы не важны) и выберите:
  - «Повторить восстановление из …»;
  - «Вернуть состояние до восстановления (pre-restore-…)».

  Если бэкапа перед восстановлением нет, второй вариант недоступен: `POST /api/maintenance/retry` отвечает `400` с кодом `BAD_TARGET` «нет бэкапа до восстановления», попытка кода при этом не расходуется. После 5 неверных попыток код заменяется новым; новый код печатается и при каждом новом сбое, и при перезапуске агента. Ввод кода ограничен 10 попытками за 15 минут с одного адреса.

- **Аварийный путь без веб-интерфейса** — `scripts/restore.sh` (см. выше). Он останавливает агент, отмечает незавершённое восстановление как выполненное вручную и очищает Redis вместе с флагом обслуживания.

## Вход через LDAP/Active Directory

Опционально, выключено по умолчанию (`LDAP_ENABLED=false`) — тогда работает только локальный admin/password,
как раньше. Переменные — в `.env.example`.

При включении (`LDAP_ENABLED=true`) `POST /api/auth/login` сначала ищет пользователя в LDAP
(`LDAP_BASE_DN` с фильтром `LDAP_USER_FILTER`, `%s` — подставляемый логин) и пытается выполнить
bind найденным DN с введённым паролем. Поиск, если `LDAP_BIND_DN` задан, выполняется от имени этой
сервисной учётной записи; иначе — анонимно (если сервер это разрешает).

- **Успешный bind.** Если локального пользователя с таким логином ещё нет, он заводится автоматически
  с ролью `LDAP_DEFAULT_ROLE` (по умолчанию `user`) и случайным, никому не известным локальным паролем
  (им нельзя войти напрямую — только через LDAP). Дальше роль, блокировка (`blocked`) и группы живут
  в БД как у обычного пользователя и LDAP их не трогает.
- **Неудача** (неверный пароль, пользователь не найден, LDAP-сервер недоступен) — не ошибка 401 сама
  по себе: API откатывается на обычную проверку локального пароля. Это специально, чтобы встроенный
  `ADMIN_LOGIN`/`ADMIN_PASSWORD` не терял доступ при сбое LDAP.
- Заблокированный (`blocked`) локальный пользователь не может войти ни через LDAP, ни локально.
- Встроенный `ADMIN_LOGIN` входит только по локальному паролю: пользователь каталога с тем же логином
  не получает его учётную запись.
- `%s` в `LDAP_USER_FILTER` заменяется во всех вхождениях, например `(|(uid=%s)(mail=%s))` — вход по
  логину или по почте. Логин экранируется (RFC 4515), поэтому `*`, `(`, `)` и `\` не расширяют фильтр.
- Если сервер LDAP не отвечает, попытка прекращается через 5 с на соединение и 10 с на операцию, после
  чего проверяется локальный пароль.
- `ldaps://` с самоподписанным сертификатом сервера LDAP — `LDAP_TLS_REJECT_UNAUTHORIZED=false`.
- Active Directory: `LDAP_USER_FILTER=(sAMAccountName=%s)`. OpenLDAP: `LDAP_USER_FILTER=(uid=%s)` (по умолчанию).

## Параметр «SQL-список»

Варианты параметра типа «SQL-список» (`query`) берутся запросом к источнику шаблона:

- **Колонки.** Запрос возвращает `value` (значение параметра) и `label` (подпись в списке). Без колонки `value` значением служит первая колонка, кроме `label`. Без колонки `label` подписью служит первая колонка, кроме колонки значения, а если её нет, само значение. Повторы значений убираются. Дата приходит как `ГГГГ-ММ-ДД`, метка времени (timestamp) — строкой ISO.
- **Зависимость.** Ссылка `:имя` на другой параметр делает список зависимым. Например, `select id as value, number as label from invoices where company_id = :companyId`. Пока обязательный родитель не выбран, поле неактивно. После смены родителя недоступное значение сбрасывается.
- **Множественный выбор.** Значение передаётся массивом. В SQL используйте `= any(:param)`, например `where id = any(:ids)`; знак `=` обязателен. Это касается и зависимых списков: если у «Компании» включён множественный выбор, «Счёт» пишется как `where company_id = any(:companyId)`. Редактор параметров подсказывает нужную форму сравнения, а ошибка SQL дополняется подсказкой, если `=` и `any` перепутаны.
- **Лимит.** Не больше 1000 вариантов. Если запрос вернул больше, это ошибка: уточните запрос.
- **Строгая проверка.** При формировании отчёта сервер заново считает варианты с выбранными значениями родителей. Значение не из списка отклоняется с ошибкой у поля.

Пример — демо-шаблон «Счёт (демо)»: «Компания» → «Счёт».

## Просмотр перед сохранением

На странице отчёта нет выбора формата. «Сформировать» собирает данные один раз и показывает отчёт в PDF; для Excel-шаблона это печатный вид по настройкам печати шаблона. Под просмотром — «Сохранить как» с кнопкой для каждого формата шаблона: Word — PDF, DOCX, ODT; Excel — PDF, XLSX, ODS; PowerPoint — PDF, PPTX. Основная кнопка — формат по умолчанию из настроек шаблона. Повторное «Сформировать» создаёт новый запуск.

- **Снимок запуска.** При формировании API сохраняет данные (`reports/<runId>/data.json`) и копию файла шаблона (`reports/<runId>/template.<ext>`) и собирает из них PDF (`out.pdf`). Другой формат собирается из того же снимка при первом запросе (`out.<формат>`), дальше отдаётся готовым. Поэтому файл совпадает с просмотром, даже если данные в источнике или шаблон уже изменились.
- **API.**
  - `POST /api/reports/:id/render` принимает `{ params }`; поле `format` игнорируется.
  - `GET /api/runs/:id/file?format=<формат>&inline=0|1` отдаёт файл нужного формата, без `format` — PDF. Формат, недоступный для шаблона, — `400 VALIDATION` «формат недоступен для этого отчёта». Удалённый снимок — `410` «файл удалён — сформируйте отчёт заново».
  - Одновременные запросы одного формата собирают файл один раз: advisory-блокировка Postgres, работает и с несколькими экземплярами API.
  - В `GET /api/runs` у запуска есть `formats` (можно скачать) и `readyFormats` (уже собраны).
- **История.** У запуска со снимком кнопка «Скачать» открывает меню со всеми форматами. Запуски, сделанные до обновления, скачиваются только в своём формате, как раньше.
- **Хранение.** Очистка по `REPORT_RETENTION_DAYS` и удаление пользователя удаляют каталог `reports/<runId>/` целиком.
  - Объём на запуск. Каждый успешный запуск хранит в `reports/<runId>/` копию шаблона (до 20 МБ, лимит multipart-загрузки), `data.json` (на каждый запрос не больше `QUERY_MAX_ROWS` строк, по умолчанию 100 000, поэтому файл может занимать десятки МБ), `out.pdf` и каждый формат, скачанный позже. Раньше запуск хранил один выходной файл.
  - Рост. Том данных и ночной бэкап `storage.tar.gz` растут примерно пропорционально числу запусков за `REPORT_RETENTION_DAYS` (по умолчанию 30) — это главный параметр, которым объём регулируется.
  - Параллельность. У каждого экземпляра API отдельный пул из 3 соединений с БД для сборки файлов: одновременно собираются не больше 3 разных файлов на экземпляр, остальные запросы ждут до срока отчёта (иначе `504`).

## Доступ к отчётам

Администраторы видят все шаблоны. Пользователь видит шаблон в каталоге и может сформировать по нему отчёт, если выполнено хотя бы одно условие:

- у шаблона включено «Доступно всем»;
- шаблон лежит в категории с «Доступно всем»;
- пользователь состоит в группе, которой открыта категория шаблона;
- пользователь состоит в группе, которой открыт сам шаблон.

Для пользователя недоступный шаблон неотличим от несуществующего: карточка, формирование и варианты SQL-списков отвечают 404.

- **Где настраивается.** Группы и их участники — раздел «Группы» (или поле «Группы» в диалоге пользователя). Категории, их «Доступно всем» и группы — раздел «Категории». Доступ шаблона — вкладка «Настройки» → «Доступ»: категория, «Доступно всем», группы. Если шаблон никому не открыт, там же видно предупреждение «доступен только администраторам».
- **Каталог.** Отчёты сгруппированы по категориям (по порядку сортировки, затем по имени), шаблоны без категории — в последнем разделе «Без категории»; категория с именем «Прочие» — обычный раздел. Если раздел один, заголовков нет.
- **После обновления.** Миграция делает все существующие шаблоны «Доступно всем», поэтому после обновления пользователи видят то же, что и раньше. Новые шаблоны (создание и загрузка) закрыты, пока администратор не откроет доступ. Копия шаблона наследует категорию, «Доступно всем» и группы оригинала.
- **История.** Закрытие доступа не трогает историю: пользователь по-прежнему видит свои прошлые запуски и скачивает их файлы, но новый отчёт по шаблону сформировать уже не может.
- **Демо.** `pnpm stack:demo` создаёт категорию «Финансы», группу «Бухгалтерия» и кладёт «Счёт (демо)» в «Финансы» с «Доступно всем».

## Справка по шаблонам

Раздел администрирования «Справка по шаблонам» (`/admin/help`) — примеры тегов Carbone, проверенные на нашей бесплатной версии (Community Edition): основы, таблицы, форматирование, условия, итоги и группировка через SQL. Последний раздел — что в бесплатной версии недоступно и чем это заменить. В редакторе шаблона ссылка «Справка по синтаксису» открывает справку в новой вкладке, документ в OnlyOffice остаётся открытым.

- API передаёт Carbone `lang: 'ru'`: `formatN(2)` даёт `1 234 567,89`, `formatC()` — `1 234 567,89 ₽`. **Вывод существующих шаблонов меняется после обновления:** `formatN`/`formatC` теперь печатают русские разделители и ₽ (`formatN(2)` для `1234567.891` было `1,234,567.89`, стало `1 234 567,89`; `formatC()` было `1,234,567.89 €`, стало `1 234 567,89 ₽`); суммы в `formatC(…,'USD')`/`convCurr` теперь пересчитываются из рублей, а не из евро, по встроенным курсам (1000 было `1,140.30 $`, стало `14,68 $`); даты не меняются.
- Если в шаблоне есть форматтер, отключённый в бесплатной версии (например, `aggSum`), формирование и предпросмотр отвечают `400` с кодом `CARBONE_COMMUNITY`: «в шаблоне используется aggSum — недоступно в бесплатной версии Carbone, см. «Справка по шаблонам»». Запуск попадает в историю с этим текстом.
- `pnpm help:check` рендерит каждый пример справки через Carbone поднятого стека (`docker compose exec` в контейнер `api`, те же `lang` и `TZ`, что у API) и сравнивает текст результата с ожидаемым; при расхождении — код выхода 1. `pnpm help:check -- --self-test` проверяет только сборку DOCX, без Docker. В CI проверка не запускается.

## Безопасность источников данных

Подключайте источники под отдельным пользователем PostgreSQL с правами только на чтение
(`GRANT SELECT`). Приложение дополнительно выполняет запросы в `READ ONLY`-транзакции с
`statement_timeout`, но права на уровне БД — основная защита.

SSL источника задаётся одним из трёх режимов:

- «Без SSL» (`disable`);
- «SSL без проверки сертификата» (`require`): трафик шифруется, но защиты от подмены сервера нет,
  поэтому используйте этот режим только во внутренней сети;
- «SSL с проверкой сертификата» (`verify`): сертификат сервера проверяется. Для самоподписанного
  или внутреннего сертификата укажите свой CA в формате PEM.

В API поле `sslMode` обязательно.

## Конфигурация

`MIGRATIONS_DIR` — необязательная папка с миграциями БД, по умолчанию `./drizzle` относительно
текущей директории процесса.

`STORAGE_BACKEND` — где API хранит файлы: `local` (по умолчанию, каталог `STORAGE_DIR`) или `s3`.
Для `s3`: `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` обязательны (иначе API не запускается:
«S3_BUCKET: обязателен при STORAGE_BACKEND=s3»); `S3_ENDPOINT` — адрес S3-совместимого хранилища
(пусто — AWS S3), `S3_REGION` (по умолчанию `us-east-1`), `S3_FORCE_PATH_STYLE` (`true` для SeaweedFS,
по умолчанию `false`), `S3_CREATE_BUCKET` (по умолчанию `false`). При старте API проверяет бакет:
если его нет, при `S3_CREATE_BUCKET=true` создаёт, иначе завершается с ошибкой «бакет S3_BUCKET не найден».
Ключи доступа в журнал не попадают. В Docker все эти значения задаёт `docker-compose.yml`.

`REPORT_TIMEOUT_MS` — общий срок формирования отчёта и предпросмотра в миллисекундах (по умолчанию
120000, то есть 2 минуты). В него входят проверка параметров (запросы вариантов SQL-списков),
запросы данных и рендер Carbone. При превышении API отвечает `504` с кодом `TIMEOUT` («превышено
время формирования отчёта»). Запросы к источнику, ещё идущие в этот момент, останавливаются не позже
чем через `QUERY_TIMEOUT_MS` после срока.
Тот же срок ограничивает сборку файла другого формата из снимка (`GET /api/runs/:id/file?format=…`).
Отсчёт идёт от начала запроса на скачивание; ожидание, пока тот же файл собирает другой запрос,
входит в срок.
`RENDER_TIMEOUT_MS` по-прежнему ограничивает только Carbone.

`BACKUP_AGENT_URL` и `BACKUP_AGENT_TOKEN` — адрес агента бэкапа и общий токен (не короче 32 символов). Без адреса управление
бэкапами в админке выключено: `/api/admin/backups*` отвечают `404` с кодом `backups_disabled`, пункта меню нет. Адрес без
токена или короткий токен — ошибка конфигурации при старте. Агент недоступен или не ответил за 10 с — `502`
`backup_agent_unavailable` «Агент бэкапа недоступен». В Docker оба значения задаёт `docker-compose.yml`
(`http://backup-agent:8080` — адрес агента внутри стека, только во внутренней сети `backup`).

## Формат ошибок

Ошибки возвращаются как `{ error: { code, message, details? } }`. У ошибок с `code: "VALIDATION"`
`details` бывает двух видов: `[{ path, message }]` при проверке схемы запроса и `{ fields }`
(поле → сообщение) при проверке параметров отчёта.

Во время восстановления из бэкапа все маршруты, кроме `GET /api/health`, `GET /api/maintenance` и
`POST /api/maintenance/retry`, отвечают `503` с кодом `maintenance` и фазой в `details.phase`. Если Redis недоступен,
API работает как обычно: режим обслуживания включает только агент бэкапа, и он всегда пишет флаг в Redis.
