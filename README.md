# Carbone Reports

Генерация отчётов на базе Carbone с редактированием шаблонов в браузере (OnlyOffice) и интерфейсом на GravityUI.

[![CI](https://github.com/SamRozhkov/carbone-report/actions/workflows/ci.yml/badge.svg)](https://github.com/SamRozhkov/carbone-report/actions/workflows/ci.yml)

Спецификация: `docs/superpowers/specs/2026-10-02-carbone-reports-design.md`.

## Разработка API

Требования: Node 22 (`nvm use`), pnpm 10 (`corepack enable`), запущенный Docker (для интеграционных тестов).

```bash
pnpm install
pnpm test          # юнит-тесты
pnpm test:int      # интеграционные (PostgreSQL в testcontainers)
pnpm typecheck && pnpm lint
```

Локальный запуск API:

```bash
docker run -d --name cr-pg -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=app -p 5432:5432 postgres:17-alpine
cp .env.example .env   # заполнить секреты
cd apps/api && node --env-file=../../.env --import tsx src/server.ts
```

## Запуск в Docker

Нужен Docker с Compose v2.24+. Первый запуск скачивает образы OnlyOffice и Carbone (несколько ГБ).

```bash
cp .env.example .env      # заполнить обязательные переменные
```

**Разработка** (API с hot reload, интерфейс на http://localhost:8080, API напрямую на :3000, PostgreSQL на :55433; порты 8080, 3000 и 55433 слушают только 127.0.0.1):

```bash
pnpm stack:dev
```

**Прод** (HTTPS в nginx; положите сертификат и ключ в `certs/fullchain.pem` и `certs/privkey.pem`;
для локальной проверки — `./scripts/dev-cert.sh`):

```bash
pnpm stack:prod
```

Редирект с HTTP на HTTPS ведёт на стандартный порт 443; если `WEB_HTTPS_PORT` другой, открывайте `https://host:<порт>` напрямую.

**Проверка работающего стека** (сначала `pnpm install` на хосте):

```bash
pnpm stack:smoke                                        # разработка, http://localhost:8080
BASE_URL=https://localhost pnpm stack:smoke --insecure  # прод с самоподписанным сертификатом
```

Если `WEB_HTTPS_PORT` не 443, укажите порт в `BASE_URL`, например `BASE_URL=https://localhost:8443`.

Остановить: `pnpm stack:down` (данные сохраняются в томах; `docker compose down -v` удалит их).

Наружу в проде открыт только nginx. Маршруты `/internal/*` закрыты: их вызывает только OnlyOffice внутри сети.
Режимы разработки и прода на одном хосте используют один проект compose, а значит общие тома `pgdata` и `storage`. Образ разработки называется `carbone-reports-api:dev` и не затирает прод-образ.

### Данные

Состояние хранится в томах `pgdata` (PostgreSQL) и `storage` (файлы шаблонов и отчётов). Тома `carbone_templates` и `oo_*` восстанавливаются сами. Резервные копии — в разделе [«Резервное копирование»](#резервное-копирование).

`POSTGRES_PASSWORD` применяется только при первом создании тома `pgdata`; позже пароль меняется внутри PostgreSQL (`ALTER USER`), а не в `.env`.

### Redis

Сервис `redis` (`redis:7-alpine`, без сохранения на диск, `maxmemory 128mb`) хранит общее для всех экземпляров API временное состояние:

- кэш шаблонов Carbone (`cr:carbone:tpl:<id>`, срок жизни 7 дней) — шаблон не загружается в Carbone заново при каждом отчёте;
- счётчики ограничения попыток входа (`cr:rl:*` — по логину, `cr:rl-ip:*` — по IP; см. [Ограничение попыток входа](#ограничение-попыток-входа)).

Бэкапить Redis не нужно: после перезапуска он пуст, и всё восстанавливается само. Адрес задаёт `REDIS_URL` (по умолчанию `redis://redis:6379`); в compose он собирается с паролем: `redis://:${REDIS_PASSWORD}@redis:6379`.

Redis требует пароль (`--requirepass`). Переменная `REDIS_PASSWORD` в `.env` обязательна (только hex: `openssl rand -hex 32`), без неё `docker compose` не запускается. Пароль проверяется при старте контейнера `redis`. Если в нём есть что-то кроме `0-9a-f`/`A-F`, контейнер завершается с сообщением «REDIS_PASSWORD: только шестнадцатеричные символы (openssl rand -hex 32)» (видно в `docker compose logs redis`), а `api` не запускается. Пароль подставляется внутри контейнера и не виден в команде (`docker inspect`), но есть в его окружении. `redis-cli` внутри контейнера берёт пароль из `REDISCLI_AUTH`, поэтому healthcheck и `docker compose exec -T redis redis-cli …` работают без `-a`. Чтобы сменить пароль, поменяйте `REDIS_PASSWORD` в `.env` и выполните `docker compose up -d redis api` (данные Redis одноразовые).

Redis подключён только к внутренней сети `cache` (`internal: true`), общей с `api`. Другие сервисы (nginx, OnlyOffice, Carbone, демо-БД) его не видят, и выхода наружу у этой сети нет.

В compose `api` при старте ждёт, пока Redis станет healthy (`depends_on`). Работа без Redis относится ко времени после запуска. Если Redis стал недоступен, API продолжает работать: кэш считается промахом (шаблон каждый раз загружается в Carbone, отчёты формируются чуть медленнее), а ограничение попыток входа считается в памяти каждого экземпляра API, пока Redis не вернётся. В журнале API появляются ошибки подключения (не чаще раза в 30 с).

### Ограничение попыток входа

Вход (`POST /api/auth/login`) ограничен двумя независимыми лимитами; срабатывает тот, что исчерпан первым, ответ — `429 TOO_MANY_ATTEMPTS`:

- **по логину** — 10 попыток в минуту на логин (без учёта регистра), «слишком много попыток входа, повторите через минуту»;
- **по IP** — 30 попыток в минуту с одного адреса при любых логинах, «слишком много попыток входа с этого адреса, повторите через минуту».

Счётчики лежат в Redis и общие для всех экземпляров API. Если Redis недоступен или отвечает ошибкой, лимиты продолжают действовать, но считаются в памяти каждого экземпляра API отдельно (при N экземплярах — до N × лимит попыток). После ошибки API 5 с не обращается к Redis, затем пробует снова; в журнале — «Redis недоступен — лимиты запросов считаются в памяти экземпляра» (не чаще раза за 5 с).

IP клиента API берёт из `X-Forwarded-For`, который дописывает nginx: доверяется ровно одному прокси (`TRUSTED_PROXY_HOPS = 1` в `apps/api/src/app.ts`, аналог `trustProxy: 1`), так что адреса, подставленные клиентом в заголовок, не учитываются. В Fastify 5 число в `trustProxy` не доверяет ни одному хопу (fail-closed): все клиенты получили бы адрес nginx и делили один общий лимит входа 30 в минуту на весь сайт. Поэтому доверие задано функцией `trustProxyHops()`. Если перед nginx стоит ещё один прокси или балансировщик, все клиенты получат его адрес и разделят один лимит — увеличьте `TRUSTED_PROXY_HOPS`, а не `trustProxy`; это изменение кода, а не настройка. Пользователи за общим NAT или корпоративным прокси тоже делят лимит по IP. Если исходный адрес клиента теряется, все клиенты делят один лимит по IP: например, при публикации портов в Docker Desktop/OrbStack (адрес шлюза хоста) или IPv6 через docker-proxy; один злоумышленник тогда может на минуту исчерпать попытки входа для всех. Если это важно, поставьте nginx в сеть хоста или используйте прокси, сохраняющий исходный адрес. Остаточный риск: код внутри контейнера, который достаёт до `api:3000` напрямую (в сети compose по умолчанию или через опубликованный в dev 127.0.0.1:3000), может подделать `X-Forwarded-For` и обойти только лимит по IP; лимит по логину это не затрагивает.

### Запуск из готовых образов

CI публикует образы после зелёных проверок:

- `ghcr.io/samrozhkov/carbone-report-api`, `ghcr.io/samrozhkov/carbone-report-web`;
- теги: `latest` и `main` — последняя сборка `main`, `sha-<коммит>`, `X.Y.Z` и `X.Y` — релизы по тегам `vX.Y.Z`.


С заданными `API_IMAGE`/`WEB_IMAGE` не используйте `pnpm stack:*`: они пересобирают локальные исходники и тегируют их под имя релиза. Применяйте `docker compose pull` и `up -d --no-build`.

Новые пакеты GHCR приватные: сделайте их публичными (Package settings → Change visibility) или войдите на сервере: `echo <token> | docker login ghcr.io -u <user> --password-stdin` (токен с правом `read:packages`).

### Обновление / выкат

Добавьте `REDIS_PASSWORD` в `.env` перед обновлением (`openssl rand -hex 32`, см. [Redis](#redis)): без неё `docker compose` не запустится.

Перед обновлением сделайте [ручной бэкап](#резервное-копирование) (`docker compose --profile backup run --rm backup now`): миграции выполняются при старте API, а миграция 0002 удаляет колонку `ssl`, поэтому откат возможен только восстановлением из копии. После этого обновления каждому пользователю один раз нужно войти заново.
`stack:smoke --carbone-restart` разрушителен (пересоздаёт carbone и удаляет том с кэшем шаблонов) и предназначен только для стендов разработки; даже на проде через localhost это даёт около 40 с простоя Carbone.

Сессионная cookie в проде помечена `Secure`, поэтому интерфейс работает только по HTTPS.

### Резервное копирование

**Что входит в бэкап:** база `app` (`pg_dump -Fc`) и файлы шаблонов и отчётов (том `storage`). Дамп и архив снимаются под одной блокировкой, поэтому они согласованы: пока идёт бэкап, API откладывает удаление файлов.

**Что не входит:**

- `.env` с `ENCRYPTION_KEY`: без него пароли источников данных из бэкапа не расшифровать;
- `certs/`;
- кэши OnlyOffice и Carbone (тома `oo_*` и `carbone_templates` восстанавливаются сами).

Храните `.env` и `certs/` отдельно и надёжно.

Каждый бэкап — каталог `backups/<ГГГГ-ММ-ДДTЧЧ-ММ-ССZ>/` (или в вашем `BACKUP_DIR`; время UTC) с файлами `db.dump`, `storage.tar.gz` и `manifest.txt` (размеры и sha256). Незавершённый бэкап остаётся с суффиксом `.partial` и не участвует в ротации. Ротация (удаление копий сверх `BACKUP_KEEP`) выполняется только после успешного бэкапа, поэтому серия неудачных запусков не удаляет старые исправные копии. Каталоги `.partial` сами не удаляются: выясните причину сбоя по журналу и удалите их вручную, например `rm -rf backups/*.partial` (когда бэкап не идёт).

**По расписанию:**

```bash
docker compose --profile backup up -d backup
```

Имя сервиса `backup` в конце обязательно: без него compose пересоздаст и остальные сервисы стека.

Переменные в `.env`:

- `BACKUP_CRON` — расписание в формате cron, по умолчанию `0 3 * * *`. Время берётся в часовом поясе `TZ` (по умолчанию `Europe/Moscow`), а не в UTC. Строка должна состоять ровно из 5 полей; иначе контейнер завершается с кодом 2 и сообщением «BACKUP_CRON: ожидается 5 полей cron» в журнале (и из-за `restart: unless-stopped` перезапускается с той же ошибкой, пока строку не исправят). Без проверки busybox `crond` молча проигнорировал бы неверное расписание;
- `BACKUP_KEEP` — сколько последних копий хранить, по умолчанию 14;
- `BACKUP_TIMEOUT` — предельное время каждого шага (`pg_dump` и архивации файлов): целое число секунд ≥ 1 без суффиксов (`3600`, а не `1h` или `60m`), по умолчанию 3600. Неверное значение проверяется при старте контейнера: он завершается с кодом 2 и сообщением «BACKUP_TIMEOUT должен быть целым числом секунд ≥1». Шаг, не уложившийся в срок, получает TERM (а через 60 с — KILL) и прерывается, копия остаётся `.partial`, а блокировка снимается — зависший бэкап не задерживает удаление файлов в API бесконечно;
- `BACKUP_DIR` — каталог на хосте, по умолчанию `./backups`.

Журнал: `docker compose --profile backup logs backup`.

**Вручную**, например перед выкатом:

```bash
docker compose --profile backup run --rm backup now
```

**Восстановление:**

```bash
scripts/restore.sh backups/<каталог>
```

Скрипт:

1. сверяет sha256 файлов с `manifest.txt`;
2. просит ввести `restore` для подтверждения;
3. приостанавливает бэкап по расписанию (сервис `backup`), если он запущен;
4. останавливает `api` и `web` (интерфейс недоступен до конца восстановления);
5. заменяет базу `app` дампом в одной транзакции: удаляет схемы `public` и `drizzle` целиком и создаёт их заново из дампа (при ошибке база остаётся прежней);
6. заменяет содержимое тома `storage` архивом (архив проверяется до удаления старых файлов);
7. очищает Redis (`FLUSHALL`; если Redis остановлен — сначала запускает его): кэш шаблонов Carbone после замены базы устарел бы, и отчёт мог бы молча сформироваться по прежнему шаблону. Счётчики попыток входа тоже сбрасываются. Если очистить не удалось, скрипт предупреждает и продолжает — тогда выполните `docker compose exec -T redis redis-cli FLUSHALL` вручную;
8. запускает `api` и `web`, затем снова `backup`.

Если шаг после остановки `api` и `web` завершился ошибкой, скрипт сообщает, успела ли замениться база, снова запускает `backup` и оставляет `api` и `web` остановленными: устраните причину и запустите скрипт снова или верните стек командой `docker compose up -d --wait api web` (если база уже заменена, а Redis не очищен, скрипт напомнит сначала очистить его).

Восстанавливать можно и в чистый стек: сначала поднимите его с тем же `.env`, затем запустите скрипт. Можно восстанавливать и в более новую версию приложения: база полностью заменяется состоянием из бэкапа (таблицы и миграции, которых в дампе нет, удаляются), а API при старте заново применит недостающие миграции.

**Копия на другой сервер** остаётся за администратором, например по cron на хосте:

```bash
rsync -a --exclude '*.partial' backups/ backup-host:/srv/carbone-reports-backups/
```

Здесь `backups/` — каталог по умолчанию (или ваш `BACKUP_DIR`). Ротацию копий на удалённой стороне настраивает администратор.

## Разработка интерфейса

Интерфейс — `apps/web` (React 19, Gravity UI, Vite). Бэкенд, OnlyOffice и Carbone берутся из dev-стека:

```bash
pnpm stack:dev                               # API, OnlyOffice, Carbone, PostgreSQL (nginx на :8080)
pnpm --filter @carbone-reports/web dev       # интерфейс с hot reload на http://localhost:5173
```

Vite проксирует `/api` и `/onlyoffice` (включая WebSocket) на `http://localhost:8080`; другой адрес стека — переменная `STACK_URL`.
Тесты интерфейса: `pnpm --filter @carbone-reports/web test`. В прод-образе (`pnpm stack:prod`) интерфейс собирается в `docker/web.Dockerfile`.

## Демо и E2E

```bash
pnpm stack:demo     # прод-стек + демо-БД + шаблон «Счёт (демо)» в категории «Финансы» (нужен DEMO_DB_PASSWORD в .env)
pnpm e2e            # E2E на Playwright (Chromium на хосте) против поднятого стека
pnpm stack:down     # остановить
```

Первый запуск E2E: `pnpm --filter @carbone-reports/e2e exec playwright install chromium`.
Отчёт — `e2e/report/index.html`; при падении trace сохраняется в `e2e/test-results/`.
E2E меняет демо-шаблон. Перед каждым прогоном он сам восстанавливает исходный файл, запросы, параметры и доступ (`e2e/global-setup.ts`); после прогона шаблон остаётся изменённым. Вручную: `pnpm demo:seed -- --reset-template`.
Пароль `DEMO_DB_PASSWORD` задаётся ролям демо-БД только при первом создании тома. Если вы поменяли его позже, пересоздайте том демо-БД (другие тома не трогаются):

```bash
docker compose --profile demo rm -sf demo-db && docker volume rm carbone-reports_demo_pgdata && pnpm stack:demo
```

## Параметр «SQL-список»

Варианты параметра типа «SQL-список» (`query`) берутся запросом к источнику шаблона:

- **Колонки.** Запрос возвращает `value` (значение параметра) и `label` (подпись в списке). Без колонки `value` значением служит первая колонка, кроме `label`. Без колонки `label` подписью служит первая колонка, кроме колонки значения, а если её нет, само значение. Повторы значений убираются. Дата приходит как `ГГГГ-ММ-ДД`, метка времени (timestamp) — строкой ISO.
- **Зависимость.** Ссылка `:имя` на другой параметр делает список зависимым. Например, `select id as value, number as label from invoices where company_id = :companyId`. Пока обязательный родитель не выбран, поле неактивно. После смены родителя недоступное значение сбрасывается.
- **Множественный выбор.** Значение передаётся массивом. В SQL используйте `= any(:param)`, например `where id = any(:ids)`; знак `=` обязателен. Это касается и зависимых списков: если у «Компании» включён множественный выбор, «Счёт» пишется как `where company_id = any(:companyId)`. Редактор параметров подсказывает нужную форму сравнения, а ошибка SQL дополняется подсказкой, если `=` и `any` перепутаны.
- **Лимит.** Не больше 1000 вариантов. Если запрос вернул больше, это ошибка: уточните запрос.
- **Строгая проверка.** При формировании отчёта сервер заново считает варианты с выбранными значениями родителей. Значение не из списка отклоняется с ошибкой у поля.

Пример — демо-шаблон «Счёт (демо)»: «Компания» → «Счёт».

## Просмотр перед сохранением

На странице отчёта нет выбора формата. «Сформировать» собирает данные один раз и показывает отчёт в PDF; для Excel-шаблона это печатный вид по настройкам печати шаблона. Под просмотром — «Сохранить как» с кнопкой для каждого формата шаблона: Word — PDF, DOCX, ODT; Excel — PDF, XLSX, ODS; PowerPoint — PDF, PPTX. Основная кнопка — формат по умолчанию из настроек шаблона. Повторное «Сформировать» создаёт новый запуск.

- **Снимок запуска.** При формировании API сохраняет данные (`reports/<runId>/data.json`) и копию файла шаблона (`reports/<runId>/template.<ext>`) и собирает из них PDF (`out.pdf`). Другой формат собирается из того же снимка при первом запросе (`out.<формат>`), дальше отдаётся готовым. Поэтому файл совпадает с просмотром, даже если данные в источнике или шаблон уже изменились.
- **API.**
  - `POST /api/reports/:id/render` принимает `{ params }`; поле `format` игнорируется.
  - `GET /api/runs/:id/file?format=<формат>&inline=0|1` отдаёт файл нужного формата, без `format` — PDF. Формат, недоступный для шаблона, — `400 VALIDATION` «формат недоступен для этого отчёта». Удалённый снимок — `410` «файл удалён — сформируйте отчёт заново».
  - Одновременные запросы одного формата собирают файл один раз: advisory-блокировка Postgres, работает и с несколькими экземплярами API.
  - В `GET /api/runs` у запуска есть `formats` (можно скачать) и `readyFormats` (уже собраны).
- **История.** У запуска со снимком кнопка «Скачать» открывает меню со всеми форматами. Запуски, сделанные до обновления, скачиваются только в своём формате, как раньше.
- **Хранение.** Очистка по `REPORT_RETENTION_DAYS` и удаление пользователя удаляют каталог `reports/<runId>/` целиком.

## Доступ к отчётам

Администраторы видят все шаблоны. Пользователь видит шаблон в каталоге и может сформировать по нему отчёт, если выполнено хотя бы одно условие:

- у шаблона включено «Доступно всем»;
- шаблон лежит в категории с «Доступно всем»;
- пользователь состоит в группе, которой открыта категория шаблона;
- пользователь состоит в группе, которой открыт сам шаблон.

Для пользователя недоступный шаблон неотличим от несуществующего: карточка, формирование и варианты SQL-списков отвечают 404.

- **Где настраивается.** Группы и их участники — раздел «Группы» (или поле «Группы» в диалоге пользователя). Категории, их «Доступно всем» и группы — раздел «Категории». Доступ шаблона — вкладка «Настройки» → «Доступ»: категория, «Доступно всем», группы. Если шаблон никому не открыт, там же видно предупреждение «доступен только администраторам».
- **Каталог.** Отчёты сгруппированы по категориям (по порядку сортировки, затем по имени), шаблоны без категории — в последнем разделе «Без категории»; категория с именем «Прочие» — обычный раздел. Если раздел один, заголовков нет.
- **После обновления.** Миграция делает все существующие шаблоны «Доступно всем», поэтому после обновления пользователи видят то же, что и раньше. Новые шаблоны (создание и загрузка) закрыты, пока администратор не откроет доступ. Копия шаблона наследует категорию, «Доступно всем» и группы оригинала.
- **История.** Закрытие доступа не трогает историю: пользователь по-прежнему видит свои прошлые запуски и скачивает их файлы, но новый отчёт по шаблону сформировать уже не может.
- **Демо.** `pnpm stack:demo` создаёт категорию «Финансы», группу «Бухгалтерия» и кладёт «Счёт (демо)» в «Финансы» с «Доступно всем».

## Справка по шаблонам

Раздел администрирования «Справка по шаблонам» (`/admin/help`) — примеры тегов Carbone, проверенные на нашей бесплатной версии (Community Edition): основы, таблицы, форматирование, условия, итоги и группировка через SQL. Последний раздел — что в бесплатной версии недоступно и чем это заменить. В редакторе шаблона ссылка «Справка по синтаксису» открывает справку в новой вкладке, документ в OnlyOffice остаётся открытым.

- API передаёт Carbone `lang: 'ru'`: `formatN(2)` даёт `1 234 567,89`, `formatC()` — `1 234 567,89 ₽`. **Вывод существующих шаблонов меняется после обновления:** `formatN`/`formatC` теперь печатают русские разделители и ₽ (`formatN(2)` для `1234567.891` было `1,234,567.89`, стало `1 234 567,89`; `formatC()` было `1,234,567.89 €`, стало `1 234 567,89 ₽`); суммы в `formatC(…,'USD')`/`convCurr` теперь пересчитываются из рублей, а не из евро, по встроенным курсам (1000 было `1,140.30 $`, стало `14,68 $`); даты не меняются.
- Если в шаблоне есть форматтер, отключённый в бесплатной версии (например, `aggSum`), формирование и предпросмотр отвечают `400` с кодом `CARBONE_COMMUNITY`: «в шаблоне используется aggSum — недоступно в бесплатной версии Carbone, см. «Справка по шаблонам»». Запуск попадает в историю с этим текстом.
- `pnpm help:check` рендерит каждый пример справки через Carbone поднятого стека (`docker compose exec` в контейнер `api`, те же `lang` и `TZ`, что у API) и сравнивает текст результата с ожидаемым; при расхождении — код выхода 1. `pnpm help:check -- --self-test` проверяет только сборку DOCX, без Docker. В CI проверка не запускается.

## Безопасность источников данных

Подключайте источники под отдельным пользователем PostgreSQL с правами только на чтение
(`GRANT SELECT`). Приложение дополнительно выполняет запросы в `READ ONLY`-транзакции с
`statement_timeout`, но права на уровне БД — основная защита.

SSL источника задаётся одним из трёх режимов:

- «Без SSL» (`disable`);
- «SSL без проверки сертификата» (`require`): трафик шифруется, но защиты от подмены сервера нет,
  поэтому используйте этот режим только во внутренней сети;
- «SSL с проверкой сертификата» (`verify`): сертификат сервера проверяется. Для самоподписанного
  или внутреннего сертификата укажите свой CA в формате PEM.

В API поле `sslMode` обязательно.

## Конфигурация

`MIGRATIONS_DIR` — необязательная папка с миграциями БД, по умолчанию `./drizzle` относительно
текущей директории процесса.

`REPORT_TIMEOUT_MS` — общий срок формирования отчёта и предпросмотра в миллисекундах (по умолчанию
120000, то есть 2 минуты). В него входят проверка параметров (запросы вариантов SQL-списков),
запросы данных и рендер Carbone. При превышении API отвечает `504` с кодом `TIMEOUT` («превышено
время формирования отчёта»). Запросы к источнику, ещё идущие в этот момент, останавливаются не позже
чем через `QUERY_TIMEOUT_MS` после срока.
Тот же срок ограничивает сборку файла другого формата из снимка (`GET /api/runs/:id/file?format=…`).
Отсчёт идёт от начала запроса на скачивание; ожидание, пока тот же файл собирает другой запрос,
входит в срок.
`RENDER_TIMEOUT_MS` по-прежнему ограничивает только Carbone.

## Формат ошибок

Ошибки возвращаются как `{ error: { code, message, details? } }`. У ошибок с `code: "VALIDATION"`
`details` бывает двух видов: `[{ path, message }]` при проверке схемы запроса и `{ fields }`
(поле → сообщение) при проверке параметров отчёта.
