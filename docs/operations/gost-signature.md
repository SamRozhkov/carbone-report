# Подпись по ГОСТ (КриптоПро ЭЦП Browser plug-in)

С 2.11.0 отчёт можно подписать квалифицированной или неквалифицированной подписью по ГОСТ Р 34.10-2012.
Ключ пользователя не покидает его компьютер: подпись ставит КриптоПро ЭЦП Browser plug-in в браузере,
на сервер уходит только хеш PDF и готовая подпись. Результат — два файла: PDF со штампом и открепленная
подпись CAdES (`.sig`). Подпись из файла `.p12` (PAdES, §39) работает как раньше.

Включается в шаблоне: вкладка «PDF» → «Электронная подпись» → «Способ подписи» → «ГОСТ, КриптоПро (файл .sig)».
Без настройки на сервере (кроме файла `cadesplugin_api.js`) всё работает.

## Что нужно на компьютере пользователя

- КриптоПро CSP 5.0 (лицензия — на стороне организации);
- КриптоПро ЭЦП Browser plug-in и расширение для браузера;
- сертификат ГОСТ Р 34.10-2012 (256 или 512 бит) с закрытым ключом в хранилище «Личное» текущего пользователя.

Браузеры: Chrome, Яндекс.Браузер, Edge, Firefox (с расширением плагина). Safari не поддерживается.
При первой подписи плагин спрашивает разрешение для сайта, ПИН-код или пароль контейнера спрашивает он же.

## Скрипт cadesplugin_api.js

Скрипт `cadesplugin_api.js` не входит в образ: его скачивают с сайта КриптоПро после принятия условий
(условия распространения не подтверждены, поэтому мы его не поставляем). Без файла в окне подписи
показывается «Не найден КриптоПро ЭЦП Browser plug-in…», сервер при этом работает как обычно.

- **Docker Compose.** Положите файл в `./cades/cadesplugin_api.js` рядом с `docker-compose.yml`. Каталог смонтирован в
  `web` как `/usr/share/nginx/cades` (только чтение); перезапуск не нужен. Файл в git не попадает.
- **Helm.** Создайте ConfigMap и укажите его имя:

  ```bash
  kubectl -n <namespace> create configmap cades --from-file=cadesplugin_api.js
  ```

  ```yaml
  web:
    cadesPluginConfigMap: cades
  ```

  ConfigMap монтируется в `/usr/share/nginx/cades`; пусто (по умолчанию) — тома нет.

Файл отдаётся по адресу `/cadesplugin_api.js` с нашего домена и с обычными заголовками безопасности.
Если файла нет, nginx отвечает `404`, а не `index.html`: иначе браузер получил бы HTML вместо скрипта.

## Служба меток времени

`SIGN_GOST_TSA_URL` — необязательный адрес службы меток времени RFC 3161 с поддержкой ГОСТ (`http`/`https`;
неверный адрес — API не запускается). Пусто — подпись без метки (CAdES-BES), задан — CAdES-T, и метка обязательна.
Обращается к службе плагин на компьютере пользователя, поэтому доступ к ней нужен оттуда, а не с сервера.
В Helm — `config.signGostTsaUrl`, в Docker — переменная из `.env`.

Ограничения меток, которые принимает сервер:

- метка с отпечатком Стрибог от службы RSA/ECDSA отклоняется;
- служба с ключом ГОСТ Р 34.10-2001 отклоняется;
- несколько атрибутов метки времени подписи в одной подписи отклоняются;
- служба КриптоПро TSP с ключом 2012 должна работать (ожидается; подтверждается ручной приёмкой).

## Что проверяет сервер и что нет

Сервер проверяет подпись своей реализацией ГОСТ (§42.4), по порядку:

1. формат: открепленная подпись, один подписант;
2. сертификат подписанта тот же, что был при подготовке;
3. алгоритм хеша — Стрибог нужной длины, `messageDigest` равен хешу PDF;
4. подпись ГОСТ Р 34.10-2012 над подписанными атрибутами верна;
5. метка времени (при заданной службе): отпечаток, подпись метки, время в пределах срока сертификата и
   не раньше подготовки (минус 5 минут) и не позже времени сервера (плюс 5 минут) — часы службы меток и
   сервера не должны расходиться больше чем на 5 минут;
6. срок действия сертификата — на время метки, иначе на время сервера.

Сервер **не** проверяет цепочку сертификатов до доверенного корня (Минцифры и др.), списки отзыва (CRL/OCSP)
и сертификат службы меток. Время из метки — справочное, а не доверенное. Подлинность сертификата подтверждает
сервис проверки: Госуслуги проверяют цепочку.

В подпись плагин включает только сертификат подписанта (`CAPICOM_CERTIFICATE_INCLUDE_END_ENTITY_ONLY`),
поэтому для подписи не нужна установленная цепочка. Если всё же появляется ошибка цепочки (`0x800B010A`),
проверьте сертификат в КриптоПро (`CheckCertificate`).

## Проверка подписи на Госуслугах

Скачайте из отчёта «PDF со штампом» и «Подпись (.sig)» и загрузите пару на
[gosuslugi.ru/pgu/eds](https://www.gosuslugi.ru/pgu/eds) (открепленная подпись: файл и подпись раздельно).
Сертификат тестового удостоверяющего центра покажется как «не доверенный» — это ожидаемо.

## Порядок байтов хеша

Сервер отдаёт `hash` в hex, и плагин получает его в `SetHashValue` в том же порядке байтов, только в верхнем
регистре: это порядок байтов `messageDigest` в CMS. Совместимость подтверждается ручной приёмкой с настоящим плагином. Если сервер отклонил
подпись настоящего плагина, сохраните файл `.sig` и поле `hash` из ответа подготовки (`POST /api/runs/:id/sign/gost/prepare`)
для разбора: порядок байтов — первый подозреваемый.

## Политика безопасности страницы (CSP)

Страница отдаёт `script-src 'self'`, а `cadesplugin_api.js` заставляет расширение подставить на страницу свой скрипт.
По документации Chromium CSP страницы не мешает скриптам расширений (Chrome, Edge) — проверить при приёмке;
в Firefox и Яндекс.Браузере поведение тоже проверяют ручной приёмкой.
CSP не ослабляется.

## Черновик подписи

Каждая подготовка пишет черновик PDF в уникальный файл `reports/<id>/out.gost.<uuid>.pdf`, а не в `out.gost.pdf`:
так неудавшееся завершение не свяжет старый хеш с новым черновиком. Истёкшие ожидания (15 минут) и черновики
удаляет ежечасная очистка.

## Обновление

Миграция `0014` применяется автоматически. Если подпись по ГОСТ не нужна, ничего делать не требуется.
