## Итоги Плана 4 (усиление)

Ветка `feat/hardening`, 8 задач. E2E: 6 тестов зелёные дважды подряд при строгой CSP, 0 нарушений. Smoke зелёный.

**Что сделано:**

- **Отзыв сессий.** У пользователя есть `session_version`, cookie несёт `sv`. Смена пароля, роли или блокировка через `PATCH` увеличивает версию. Админ завершает сессии кнопкой «Завершить сессии» (`POST /api/users/:id/sessions/revoke`), пользователь — кнопкой «Выйти везде» (`POST /api/auth/logout-all`). E2E `sessions.spec.ts`: после отзыва следующий переход пользователя ведёт на `/login`.
- **SSL источников.** Режимы `disable`/`require`/`verify`, для `verify` можно указать свой CA (PEM). Миграция переводит `ssl=true` в `require`.
- **Callback OnlyOffice.** Старые токены отклоняются: `exp` проверяется с допуском 60 с, без `exp` принимается только `iat` не старше 600 с и не из будущего (повтор в этом окне возможен). Document Server 9.4 присылает `exp`.
- **Файлы шаблонов с версией.** Пути `templates/<id>/v<N>.<ext>`. Callback скачивает файл вне блокировки строки. Миграция при старте переносит старые файлы (на демо-стенде перенесено 2).
- **Carbone и тесты.** Реальный ответ «Template not found» зафиксирован, повторная загрузка проверена в smoke (`--carbone-restart`). Добавлены тесты пагинации `/api/runs` и ответа 410.

**Решения по ходу:**

- После выката старые cookie без `sv` недействительны: всем нужно войти заново.
- Правка своей учётной записи выдаёт новую cookie, только если `sv` не изменилась с момента проверки сессии. Иначе запрос, начатый до отзыва, получил бы свежую cookie.
- `sslMode` в API обязателен. Иначе клиент старого формата (`{ ssl: true }`) молча переключил бы источник на соединение без шифрования.
- Переключатель SSL в форме — группа (`role="group"`), а не `<label>`: клик по заголовку поля не выбирает «Без SSL».
- Если старую версию файла удалили во время рендера, рендер берёт текущий файл.
- `smoke --carbone-restart` удаляет том `carbone_templates`. Поэтому он работает только с локальным `BASE_URL` (loopback) и ждёт готовности Carbone до 120 с.

## Итоги Плана 6 (бэкапы)

- **Сервис `backup`** (профиль `backup`, образ `postgres:17-alpine`, скрипты в `docker/backup/`):
  - режим `cron` — busybox `crond` по `BACKUP_CRON` в часовом поясе `TZ` (по умолчанию `Europe/Moscow`);
  - режим `now` — один бэкап (`docker compose --profile backup run --rm backup now`);
  - режим `restore-storage` — распаковка архива в `/data`; вызывается из `scripts/restore.sh`.
- **Согласованность:** `pg_dump` и `tar` идут под исключительной advisory-блокировкой `726100001`. Удаления файлов в API ждут её через отдельный пул (`max 2`), а `discardUncommittedFile` её не ждёт: пропускает удаление, если идёт бэкап (остаётся безвредный файл-сирота).
- **Каталог бэкапа:** `backups/<UTC-время>/` с `db.dump`, `storage.tar.gz`, `manifest.txt` (размеры, sha256, последняя миграция). Незавершённые — `.partial`, в ротации не участвуют. `BACKUP_KEEP` — целое ≥ 1, ведущие нули отбрасываются (`014` → 14, `00` отклоняется).
- **Восстановление** (`scripts/restore.sh`): sha256 → подтверждение `restore` → пауза сервиса `backup` (если запущен) → стоп `api`/`web` → замена базы в одной транзакции (`DROP SCHEMA drizzle, public CASCADE` + SQL из `pg_restore --no-owner`, `psql -1`) → распаковка `storage` → старт `api`/`web` и `backup`. При ошибке после остановки ловушка `EXIT` сообщает, заменена ли уже база, снова запускает `backup` и подсказывает, как вернуть стек. Проверено на живом стеке: в существующий стек (удалённый шаблон вернулся вместе с файлом, smoke и E2E зелёные) и в чистый стек после `down -v` (smoke зелёный).
  - Хранилище восстанавливается через `docker run` образа `postgres:17-alpine` с полным именем тома (`<проект>_storage`, ищется по меткам compose), а не через `docker compose run -v storage:/data`: compose сливает такой `-v` с `storage:/data:ro` сервиса, и том остаётся только для чтения (и с коротким, и с полным именем тома).
- **Не входит в бэкап:** `.env` (`ENCRYPTION_KEY`), `certs/`, кэши OnlyOffice и Carbone. Копирование бэкапов на другой сервер — за администратором.
- **Финальное ревью, исправлено:**
  - I1: удаление прежнего файла шаблона после сохранения (callback OnlyOffice, `PUT /api/templates/:id/file`) идёт в фоне — сохранение во время бэкапа не ждёт его окончания (int-тест с удержанной блокировкой);
  - I2: восстановление в стек с более новой схемой — схемы `public` и `drizzle` удаляются целиком в той же транзакции, что и загрузка дампа (проверено вживую: лишняя таблица и «будущая» миграция исчезают);
  - очистка отчётов сначала помечает `file_deleted`, потом удаляет файл; `tar` исключает `*.tmp`; `restore.sh` отказывается работать во время ручного бэкапа; `persist-credentials: false` во всех `actions/checkout`.
- **Отложено (не блокирует):**
  - T1: в тестах шлюза остаются проверки через фиксированный `sleep`; таймер вспомогательной `bounded()` не очищается;
  - T2: нет ограничения времени удержания блокировки бэкапом (зависший `pg_dump` держит удаления файлов в API); у ожидания блокировки в API нет верхней границы; ротация полагается на монотонные часы (имена-даты); `BACKUP_CRON` не проверяется — busybox crond молча игнорирует неверную строку;
  - T3: если `docker compose stop backup` в `restore.sh` частично не удался, скрипт прерывается до остановки `api`/`web`, но сервис `backup` может остаться в промежуточном состоянии — проверить вручную.
- **CI (гигиена):** все actions закреплены по SHA актуальных релизов (Node 24), добавлен `.github/dependabot.yml` (`github-actions` еженедельно, `npm` ежемесячно с группой minor/patch). - **Тип параметра `query` («SQL-список»):**
  - поля `sql` и `multiple`;
  - варианты берутся запросом к источнику шаблона: значение — колонка `value`, иначе первая колонка, кроме `label`; подпись — колонка `label`, иначе первая колонка, кроме колонки значения (если её нет — само значение); повторы значений убираются;
  - не больше 1000 вариантов, при превышении — ошибка;
  - ссылки `:имя` задают зависимости. Граф проверяется при сохранении параметров (неизвестные имена, циклы);
  - при множественном выборе значение — массив, в SQL используется `= any(:param)`.
- **API:**
  - `POST /api/templates/:id/params/:name/options` возвращает `{options, waitingFor?}`. Пока обязательный родитель не задан, запрос не выполняется;
  - при формировании отчёта значения строго проверяются: варианты пересчитываются с выбранными родителями, все запросы идут в одной транзакции;
  - пользователь получает `sql: null` и `dependsOn`.
- **Интерфейс:**
  - `QueryParamField` — Select с фильтром. Варианты грузятся для каждого набора значений родителей;
  - пока обязательный родитель не выбран, поле неактивно с подсказкой «сначала выберите: …»;
  - при смене родителя недоступное значение сбрасывается;
  - в редакторе параметров есть поле SQL, флажок множественного выбора, строка «зависит от» и кнопка «Проверить»;
  - значение по умолчанию вводится как есть (пробелы внутри сохраняются), а пробелы по краям обрезаются при сохранении параметров;
  - после сохранения параметров кэш вариантов шаблона сбрасывается.
- **Демо:**
  - в «Счёт (демо)» добавлены зависимые параметры «Компания» (`companyId`) → «Счёт» (`invoiceId`), по умолчанию 1/1;
  - запросы отчёта не менялись;
  - E2E `sql-params.spec.ts` выбирает «АО «Лютик»», проверяет, что в «Счёт» доступен только СЧ-002, проверяет DOCX и возврат к СЧ-001.
- **Живой прогон:** E2E 7/7 зелёные дважды подряд. Smoke зелёный со второй попытки: первая пришлась на внутренний перезапуск docservice в OnlyOffice сразу после старта (healthcheck 502).
- **Отложено (не блокирует):**
  - значения по умолчанию не приводятся к типу варианта (`'1'` против `1`; сравнение идёт через `String`, поэтому работает);
  - подсказка и неактивность поля расходятся, когда `waitingFor` приходит с сервера;
  - слабый тест на отсутствие цикла обновлений;
  - вложенные кавычки в ключе ошибки SQL вариантов;
  - SQL_ERROR и TOO_MANY_OPTIONS при рендере записываются как неудачный запуск;
  - проверка значений и сам отчёт читают данные в разных транзакциях (разные снимки): между ними значение может стать недопустимым;
  - текст ошибки pg в SQL вариантов виден пользователю (так же, как у запросов отчёта);
  - родитель типа «строка» вызывает запрос вариантов на каждое нажатие клавиши (нет debounce);
  - в истории запусков массивы показываются как «1,2».
- **Исправлено по итогам финального ревью:**
  - I1: множественное значение по умолчанию в редакторе набирается как текст («1, 2»); разбор по запятым, обрезка и отбрасывание пустых — при сохранении параметров;
  - m1: даты и время (`Date`) в вариантах передаются строкой ISO, а не `String(Date)`;
  - m2: правило выбора колонок вариантов при одной из колонок `value`/`label` (см. выше и README);
  - m3: варианты зависимого параметра строго проверяют всех предков, как при генерации: недопустимое значение предка → `waitingFor` с прямым родителем, варианты не выдаются;
  - m7: повторы значений в вариантах убираются, остаётся первое.

## Итоги Плана 8 (группы и доступ)

- **Правило доступа** (`apps/api/src/modules/access/access.ts`, одно на весь API): админ видит всё; пользователь — шаблон с «доступно всем», шаблон в категории с «доступно всем», шаблон в категории, открытой его группе, или шаблон, открытый его группе. Недоступный шаблон для пользователя отвечает 404 (карточка, формирование, варианты SQL-списков). История запусков и файлы прошлых отчётов доступом не фильтруются.
- **Миграция `0004_access`:** таблицы групп, категорий и связей; все существующие шаблоны получают `public = true`. Новые шаблоны (создание, загрузка) закрыты. Копия наследует категорию, `public` и группы.
- **API (только админ):** `/api/groups` (+ `PUT /members`), `/api/categories` (+ `PUT /groups`), `GET/PUT /api/templates/:id/access`, `GET/PUT /api/users/:id/groups`; `UserDto.groupIds`, `TemplateSummary.category`. Гонка «удалили связанную строку» (FK 23503) → 400; PATCH групп и категорий частичный.
- **Интерфейс:**
  - страницы «Группы» (диалог «Участники») и «Категории»; поле «Группы» в диалоге пользователя и колонка «Группы» в таблице (пока группы грузятся — «…», при ошибке — «Не удалось загрузить группы»);
  - «Настройки» → «Доступ»: категория, «Доступно всем», группы, «Сохранить доступ»; предупреждение «сейчас доступен только администраторам», а при несохранённых правках — «после сохранения будет доступен только администраторам»;
  - `EditUserDialog` обновляет списки в `onSettled`: успешный PATCH виден, даже если следующий PUT групп упал;
  - каталог «Отчёты» сгруппирован по категориям (`sortOrder`, затем имя; «Прочие» последним); при одном разделе заголовков нет; поиск скрывает пустые разделы.
- **Демо:** `demo-seed` идемпотентно создаёт категорию «Финансы» (`sortOrder` 1, не public) и группу «Бухгалтерия», а «Счёт (демо)» кладёт в «Финансы» с `public = true` (на свежей БД загруженный шаблон иначе был бы закрыт). `e2e/global-setup.ts` возвращает тот же доступ перед прогоном.
- **E2E `access.spec.ts`:** копия демо-шаблона «Закрытый <ts>» без доступа → пользователь не видит её в каталоге, прямая ссылка даёт «шаблон не найден» → админ в UI открывает шаблон группе и добавляет в неё пользователя (два участника за одно открытие мультиселекта в диалоге, проверка через `getByRole('option')`) → пользователь после обновления видит шаблон и формирует PDF. Проблема `aria-hidden` у мультиселекта в диалоге в живом Chromium не воспроизвелась, `disablePortal` не понадобился.
- **Живой прогон:** проверены оба пути — существующая БД (миграция 0004) и свежая (том `pgdata` пересоздан). На свежей БД первый прогон E2E упал в `access.spec`: «Сформировать» нажималось до подстановки значений по умолчанию зависимых SQL-списков; добавлено ожидание, как в `user.spec`. После этого E2E 8/8 дважды подряд, smoke зелёный.
- **Отложено (не блокирует):**
  - API: блокировки родителей `FOR UPDATE` против `KEY SHARE` у FK могут дать deadlock (40P01 → 500) — перейти на `FOR NO KEY UPDATE`; нет теста коллизии имени при PATCH только имени; тест гонки опирается на `sleep` 200 мс; пробелы в тестах (дубликат при PATCH категории, пробелы в имени, диапазон `sortOrder`, каскад `category_groups`); квадратичная сборка списков; дублируется хелпер `userGroupIds`;
  - интерфейс: в «Доступе» нет подсказки об устаревших данных; для неизвестной категории предупреждение не показывается; заголовок `CategoryDialog` после частичной ошибки; нет тестов повторов после частичной ошибки;
  - категория с именем «Прочие» в каталоге неотличима по заголовку от раздела шаблонов без категории.
