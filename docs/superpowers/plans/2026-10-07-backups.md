# Carbone Reports — План 6: резервное копирование и гигиена CI

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Согласованные бэкапы базы и хранилища по расписанию без остановки API. Проверенное восстановление одной командой. CI без устаревших actions и двойных прогонов.

**Architecture:**
- Удаления файлов в API проходят через шлюз с разделяемой advisory-блокировкой Postgres.
- Сервис `backup` (профиль compose) держит исключительную блокировку на время `pg_dump` и `tar` в одной сессии `psql`. Расписание задаёт busybox `crond`.
- Восстановление — скрипт на хосте.

**Tech Stack:** Postgres 17 advisory locks, `postgres:17-alpine` (pg_dump, psql, crond), POSIX sh, Docker Compose profiles, GitHub Actions, Dependabot.

**Spec:** `docs/superpowers/specs/2026-10-02-carbone-reports-design.md`, §17.

## Global Constraints

- Ключ блокировки — `726100001`. Константа `STORAGE_REMOVE_LOCK_KEY` в API и переменная `LOCK_KEY` в скрипте бэкапа.
- Через шлюз проходит только `Storage.remove`. `write` и `read` не блокируются.
- Шлюз держит отдельное соединение пула только на время одного удаления. Соединение из пула транзакции drizzle не используется.
- Скрипты `docker/backup/*.sh` пишутся на POSIX `sh` (busybox/ash), без bash-измов. Проверка: `sh -n` и `shellcheck -s sh`, если доступен.
- Хранилище монтируется в сервис `backup` только для чтения. Восстановление монтирует его на запись только в одноразовом контейнере.
- Сообщения скриптов и README — на русском.
- Пуш на GitHub: только ветка `feat/backups` (Task 4). В `main` не пушить.
- Гейты: `pnpm typecheck && pnpm lint && pnpm exec prettier --check . && pnpm test`. Задачи с изменениями в API — плюс `pnpm test:int`.
- Docker на OrbStack. Перед `up`/`build` проверять `df -h /System/Volumes/Data`: при остатке меньше 2 ГБ — BLOCKED. Удалять только висячие образы `carbone-reports`. В конце задачи — `docker compose --profile demo --profile backup down` без `-v`.

## Review Focus

1. **Бэкап идёт во время сохранения шаблона.** Ожидание: после восстановления у каждой строки `templates.file_path` есть файл. Проверка: Task 1 (интеграционный тест шлюза) и Task 3 (живое восстановление).
2. **API ждёт шлюз, держа блокировку строки.** Ожидание: нет дедлока с `pg_dump`. `pg_dump` берёт только `ACCESS SHARE` и не конфликтует с `FOR UPDATE` строк. Проверка: Task 1, тест с удержанием исключительной блокировки во время `DELETE`.
3. **Бэкап упал на середине.** Ожидание: остаётся `*.partial`, он не считается копией и не участвует в ротации, выход ненулевой. Проверка: Task 2.
4. **Восстановление в стек с другим паролем Postgres или после `down -v`.** Ожидание: `pg_restore --no-owner` работает в свежую базу, том создаётся. Проверка: Task 3.
5. **Ветка без PR после смены триггеров CI.** Ожидание: её можно прогнать через `workflow_dispatch`. Проверка: Task 4.

```ts
/** Обёртка вокруг удаления: бэкап приостанавливает удаления, чтобы дамп и архив совпадали. */
export type RemoveGate = <T>(fn: () => Promise<T>) => Promise<T>;
const passThrough: RemoveGate = (fn) => fn();

export class Storage {
  private readonly root: string;

  constructor(
    root: string,
    private readonly removeGate: RemoveGate = passThrough,
  ) {
    this.root = resolve(root);
  }
  // ...
  /** Удаляет файл или каталог целиком; отсутствие — не ошибка. Ждёт, пока идёт бэкап. */
  async remove(rel: string): Promise<void> {
    const abs = this.path(rel);
    await this.removeGate(() => rm(abs, { recursive: true, force: true }));
  }
```

```ts
      inside++;
      maxInside = Math.max(maxInside, inside);
```

- [ ] **Step 4: Шлюз**

`apps/api/src/lib/storage-gate.ts`:
```ts
import type pg from 'pg';
import type { RemoveGate } from './storage';

/** Общий с docker/backup/backup.sh ключ: бэкап берёт его исключительно, удаления — разделяемо. */
export const STORAGE_REMOVE_LOCK_KEY = 726100001;

export function createRemoveGate(pool: pg.Pool): RemoveGate {
  return async (fn) => {
    const client = await pool.connect();
    try {
      await client.query('select pg_advisory_lock_shared($1)', [STORAGE_REMOVE_LOCK_KEY]);
      try {
        return await fn();
      } finally {
        await client.query('select pg_advisory_unlock_shared($1)', [STORAGE_REMOVE_LOCK_KEY]);
      }
    } finally {
      client.release();
    }
  };
}
```

- [ ] **Step 1: Скрипты**

`docker/backup/backup.sh`:
```sh
#!/bin/sh
# Один бэкап: дамп базы и архив хранилища под исключительной advisory-блокировкой
# (API на это время откладывает удаления файлов — дамп и архив согласованы).
set -eu
: "${PGHOST:=postgres}" "${PGUSER:=app}" "${PGDATABASE:=app}" "${LOCK_KEY:=726100001}"
: "${BACKUP_KEEP:=14}"
export PGHOST PGUSER PGDATABASE
: "${PGPASSWORD:?не задан PGPASSWORD}"

name=$(date -u +%Y-%m-%dT%H-%M-%SZ)
dir="/backups/$name.partial"
mkdir -p "$dir"
echo "бэкап $name: начало"

psql -v ON_ERROR_STOP=1 -q <<SQL
select pg_advisory_lock($LOCK_KEY);
\! pg_dump -Fc -f "$dir/db.dump" || exit 3
\! tar -czf "$dir/storage.tar.gz" -C /data . || exit 4
select pg_advisory_unlock($LOCK_KEY);
SQL
```
Проверьте, как `psql` обрабатывает ненулевой код `\!`. Если `ON_ERROR_STOP` не прерывает скрипт по коду shell-команды (скорее всего, так и есть), сделайте иначе. После блока `psql` проверьте, что оба файла существуют и непусты, иначе завершитесь с ошибкой, оставив `.partial`. Если нужен надёжный способ, используйте в `\!` маркер: `\! pg_dump ... && touch "$dir/.dump-ok"`.

Продолжение:
```sh

echo "бэкап $name: готово"

# Ротация: только завершённые каталоги с именем-датой, новые сверху.
```

`docker/backup/entrypoint.sh`:
```sh
#!/bin/sh
set -eu
case "${1:-cron}" in
  now) exec /backup/backup.sh ;;
  restore-storage)
    # Используется scripts/restore.sh: распаковывает архив в /data (том смонтирован на запись этим run).
    [ -f /restore/storage.tar.gz ] || { echo "нет /restore/storage.tar.gz" >&2; exit 1; }
    find /data -mindepth 1 -delete
    tar -xzf /restore/storage.tar.gz -C /data
    echo "хранилище восстановлено" ;;
  cron)
    : "${BACKUP_CRON:=0 3 * * *}"
    mkdir -p /etc/crontabs
    # crond не передаёт окружение заданиям — сохраняем нужные переменные.
    env | grep -E '^(PG|BACKUP_|LOCK_KEY|TZ)' | sed 's/^/export /; s/=\(.*\)$/="\1"/' > /backup.env
    echo "$BACKUP_CRON . /backup.env && /backup/backup.sh" > /etc/crontabs/root
    echo "расписание бэкапа: $BACKUP_CRON"
    exec crond -f -l 6 ;;
  *) echo "режимы: cron | now | restore-storage" >&2; exit 2 ;;
esac
```
Экранирование значений в `/backup.env`: пароль Postgres в проекте — hex (см. `.env.example`), поэтому простое заключение в кавычки достаточно. Опишите это в комментарии.

- [ ] **Step 1: Скрипт**

`scripts/restore.sh`:
```sh
#!/bin/sh
# Восстановление из каталога бэкапа: БД app и том storage. Останавливает api и web.
set -eu
dir=${1:?использование: scripts/restore.sh backups/<каталог>}
dir=$(cd "$dir" && pwd)
for f in db.dump storage.tar.gz manifest.txt; do [ -f "$dir/$f" ] || { echo "нет $dir/$f" >&2; exit 1; }; done

echo "Проверка контрольных сумм…"
for f in db.dump storage.tar.gz; do
  want=$(grep "^$f " "$dir/manifest.txt" | sed 's/.*sha256=//')
  got=$( (sha256sum "$dir/$f" 2>/dev/null || shasum -a 256 "$dir/$f") | cut -d' ' -f1)
  [ "$want" = "$got" ] || { echo "контрольная сумма $f не совпадает" >&2; exit 1; }
done

echo "Будут ЗАМЕНЕНЫ база app и файлы хранилища данными из $(basename "$dir")."
printf 'Введите restore для продолжения: '
read -r answer
[ "$answer" = restore ] || { echo "отменено"; exit 1; }

docker compose stop api web
docker compose up -d --wait postgres
docker compose exec -T postgres pg_restore -U app -d app --clean --if-exists --single-transaction --no-owner < "$dir/db.dump"
docker compose --profile backup run --rm --no-deps \
  -v storage:/data -v "$dir":/restore:ro backup restore-storage
docker compose start api web
docker compose up -d --wait api web
echo "Восстановление завершено."
```
Важно: `-v storage:/data` в `docker compose run` должен смонтировать **проектный** том, а не создать глобальный том `storage`, и переопределить `:ro` из сервиса. Проверьте на живом стеке. После распаковки файлы должны появиться в томе, который видит `api`.

Если compose трактует имя как глобальный том, используйте `docker volume ls` с меткой `com.docker.compose.volume=storage` и проектом из `docker compose config --format json` (поле `name`) и передайте полное имя тома. Учтите и вариант, когда сервис уже монтирует `/data` как `:ro`: если повторный `-v` для того же пути не переопределяет монтирование, используйте `docker run --rm` с образом `postgres:17-alpine` и полным именем тома вместо `compose run`.
