# 2.0.1: дренаж, обслуживание, срок готовности потока, hideBegin — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Закрыть отложенное финальным ревью Плана 17: отчёты не падают при остановке пода, режим обслуживания не мешает конвертации, зависший при загрузке поток пересоздаётся, отличие `hideBegin` от EE устранено (если без регрессий).

**Architecture:** Рендерер считает активные отчёты и даёт `idle()`; `server.ts` по сигналу ставит флаг остановки (readiness 503 на новом `/api/ready`), ждёт `idle()` не дольше срока рендера и только потом закрывает приложение. Пул получает таймер готовности. Белый список обслуживания расширяется префиксом `/internal/render-files/`. Правка разбора `[i+1]` в `packages/carbone`.

**Tech Stack:** Node 22, Fastify 5, vitest, `worker_threads`, Helm 4 + helm-unittest, mocha (packages/carbone).

**Spec:** `docs/superpowers/specs/2026-10-02-carbone-reports-design.md`, §29.

## Global Constraints

- Ветка `feat/2.0.1-hardening`. Слияние в `main` и тег `v2.0.1` — только контроллер после зелёного CI (владелец разрешил).
- Node 22: `export PATH=$HOME/.nvm/versions/node/v22.17.0/bin:$PATH` перед `pnpm`/`node`.
- Тексты для пользователя, журналы и комментарии — на русском, в стиле окружающего кода.
- Секреты не печатаются; `.env` и `certs/` не коммитятся.
- Каждый коммит заканчивается строкой `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Перед коммитом: `pnpm exec prettier --check .`, `pnpm lint`, `pnpm typecheck` — зелёные; тесты затронутых пакетов — зелёные.
- Диск тесный (≈3 ГиБ): образы не собирать, контейнеры не поднимать; интеграционные тесты с Docker не запускать локально (их гоняет CI).
- Правило чистой реализации для `packages/carbone`: код образа `carbone-ee` не читается; ориентир — эталоны `test/golden`.
- `GET /api/health` не меняет поведения (startup/liveness).

## Review Focus

1. SIGTERM во время PDF-отчёта: Document Server успевает забрать файл, отчёт отдаётся 200, потом процесс выходит. Тест: Task 3 (модульный тест `drainAndClose`: закрытие ждёт `idle()`, срок ограничен).
2. SIGTERM без активных отчётов — выход сразу, без ожидания срока. Тест: Task 3.
3. Отчёт висит дольше срока дренажа — закрытие всё равно происходит по сроку. Тест: Task 3.
4. Режим обслуживания включён посреди конвертации — `/internal/render-files/<id>?t=…` отдаёт файл, остальные маршруты 503. Тест: Task 1.
5. Поток, повисший при загрузке модулей, — пересоздаётся, задача из очереди выполняется другим (или новым) потоком до срока. Тест: Task 2.

### Task 2: срок готовности потока рендера

**Files:**

- Create: `apps/api/src/modules/render/test-workers/never-ready.mjs`
- Test: `apps/api/src/modules/render/pool.test.ts`

**Interfaces:**
- Produces: `RenderPoolOptions.readyTimeoutMs?: number` (по умолчанию 30 000).

- [ ] Step 1: фикстура `never-ready.mjs` — поток не шлёт `{ ready: true }` и держит цикл событий (`setInterval(() => {}, 1000)`).
- [ ] Step 2: тест — пул с `never-ready`, `readyTimeoutMs: 100`: в течение ~1,5 с `onCrash` вызван хотя бы раз с `{ hadTask: false, beforeReady: true }` и ошибкой, в тексте которой есть «не готов»; `destroy()` завершается без висящих таймеров.
- [ ] Step 3: тест — задача, поставленная в пул из `never-ready`, отклоняется `RenderTimeoutError` по своему сроку (не висит дольше).
- [ ] Step 4: реализация — в `spawn` таймер `readyTimer = setTimeout(..., readyTimeoutMs)`; срабатывание: если поток всё ещё тот же и `!slot.ready` — `crash(slot, new Error('поток рендера не готов за N мс'))` (тот же путь, что авария до готовности: terminate, нарастающая пауза). Таймер снимается при `{ready:true}`, в `retire`/`crash`/`destroy`. Повторный `crash` от последующего `exit` того же потока не должен порождать второй respawn — проверить существующую защиту (по ссылке на `slot.worker`) и при необходимости добавить.
- [ ] Step 5: весь `pool.test.ts` зелёный 3 прогона подряд (`pnpm --filter api exec vitest run src/modules/render/pool.test.ts`), коммит `feat(api): срок готовности потока рендера`.

### Task 3: дренаж при остановке

**Files:**
- Modify: `apps/api/src/modules/render/renderer.ts`, `apps/api/src/server.ts`
- Create: `apps/api/src/lib/drain.ts`
- Test: `apps/api/src/modules/render/renderer.test.ts`, `apps/api/src/lib/drain.test.ts`
- Modify: `charts/carbone-reports/templates/api.yaml`, `charts/carbone-reports/tests/api_test.yaml`
- Modify: `README.md` (раздел про остановку/обновление и про `/api/ready` — найти, где описаны пробы или Helm), `docs/superpowers/notes/2026-10-02-backend-follow-ups.md`

**Interfaces:**
- Consumes: `AppDeps.drain` из Task 1.
- Produces:
  - `createEmbeddedRenderer(...)` возвращает `CarboneRenderer & { active(): number; idle(): Promise<void> }`. Счётчик увеличивается в начале `render` и уменьшается в `finally` (в том числе при ошибках); `idle()` резолвится сразу при 0, иначе — при переходе в 0.
  - `lib/drain.ts`: `export async function drainAndClose(opts: { idle: () => Promise<void>; active: () => number; timeoutMs: number; close: () => Promise<void>; log: { info(o: object, m: string): void; warn(o: object, m: string): void } }): Promise<'idle' | 'timeout'>` — пишет в журнал начало (`{ active }`, «остановка: ждём активные отчёты»), ждёт `idle()` или `timeoutMs` (таймер снимается), пишет итог, вызывает `close()` и возвращает результат.

- [ ] Step 1: тесты рендерера — `active()` = 1 во время рендера (пул-заглушка с отложенным промисом), 0 после успеха и после ошибки; `idle()` резолвится только после завершения; при 0 — сразу.
- [ ] Step 2: тесты `drainAndClose` (fake timers или короткие сроки): (а) активных нет — `close` вызван сразу, результат `'idle'`; (б) активный отчёт завершается через 50 мс — `close` вызван после него, `'idle'`; (в) отчёт не завершается — `close` вызван по сроку 100 мс, `'timeout'`, журнал `warn`.
- [ ] Step 3: реализация `renderer.ts` и `lib/drain.ts`.
- [ ] Step 4: `server.ts` — `let draining = false; deps.drain = { isDraining: () => draining }` (передать в `deps` до `buildApp`). `shutdown(signal)`: защита от повторного вызова; `draining = true`; `stopCleanup()`; `await drainAndClose({ idle: carbone.idle, active: carbone.active, timeoutMs: config.renderTimeoutMs + 5000, close: () => app.close(), log: app.log })`; дальше — прежняя последовательность закрытия (без повторного `app.close()`).
- [ ] Step 5: чарт — `readinessProbe.httpGet.path: /api/ready`; комментарий над пробами обновить (`/api/ready` проваливается при остановке, чтобы снять под с балансировки, пока доделываются отчёты); `terminationGracePeriodSeconds: {{ add (div (add .Values.config.renderTimeoutMs 999) 1000) 30 }}` в spec пода api (проверить, что `renderTimeoutMs` — число; `toString` не нужен). helm-unittest: readiness → `/api/ready`, liveness/startup → `/api/health`; `terminationGracePeriodSeconds` = 150 при значении по умолчанию 120000 и = 61 при `renderTimeoutMs: 30500`.
- [ ] Step 6: README — коротко: при остановке API ждёт активные отчёты до `RENDER_TIMEOUT_MS + 5 с`, readiness — `/api/ready`. Заметка «Итоги Плана 17»: пункты про дренаж, режим обслуживания и таймаут готовности отметить как сделанные в 2.0.1 (одной строкой «2.0.1: …», без переписывания истории).
- [ ] Step 7: `pnpm --filter api test` (модульные), helm-unittest чарта (как в CI: `docker run --rm -v "$PWD/charts:/charts" alpine/helm:4.3.0 …` только если образ уже есть локально — `docker image ls alpine/helm`; иначе пропустить и указать в отчёте, CI проверит), lint/typecheck/prettier, коммит `feat: дренаж отчётов при остановке API`.
