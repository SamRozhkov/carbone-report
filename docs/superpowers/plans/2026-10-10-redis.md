# Carbone Reports — План 9: Redis, общий срок отчёта, доработки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Перенести лимит попыток входа и кэш шаблонов Carbone в Redis.
- Ввести общий срок формирования отчёта.
- Улучшить форму отчёта: задержка запроса вариантов, неактивная кнопка «Сформировать» на время загрузки, отображение массивов в истории.
- Ограничить бэкап по времени и проверять `BACKUP_CRON`.
- Поправить Dependabot.

**Architecture:**
- В compose появляется сервис `redis`.
- Новый модуль `apps/api/src/lib/redis.ts` создаёт клиент ioredis с короткими таймаутами, чтобы недоступный Redis не задерживал запросы.
- Кэш Carbone выносится за интерфейс `TemplateIdCache` с реализациями: в памяти (для тестов) и в Redis.
- Лимит входа передаёт клиента Redis в `@fastify/rate-limit`.
- Срок отчёта задаёт объект дедлайна, который передаётся в `collectReportData` и `renderReport`.

**Tech Stack:** Redis 7, ioredis 5, `@fastify/rate-limit` 11 (опция `redis`), testcontainers (GenericContainer `redis:7-alpine`), React, TanStack Query, busybox `timeout`.

**Spec:** `docs/superpowers/specs/2026-10-02-carbone-reports-design.md`, §20.

## Global Constraints

- `REDIS_URL`, по умолчанию `redis://redis:6379`.
- Клиент ioredis: `maxRetriesPerRequest: 1`, `enableOfflineQueue: false`, `connectTimeout: 2000`, `commandTimeout: 500`, `lazyConnect: false`. Ошибки клиента пишутся в лог не чаще раза в 30 с.
- Ключи Redis имеют префикс `cr:`: `cr:carbone:tpl:<id>`; лимитер — `cr:rl:` (через `nameSpace`).
- Срок жизни кэша Carbone — `7 * 24 * 3600` с.
- `REPORT_TIMEOUT_MS`, по умолчанию 120000. Ошибка при превышении: `AppError('TIMEOUT', 504, 'превышено время формирования отчёта')`.
- Задержка (debounce) запроса вариантов — 400 мс.
- `BACKUP_TIMEOUT`, по умолчанию 3600 с.
- Тексты на русском.
- Гейты: `pnpm typecheck && pnpm lint && pnpm exec prettier --check . && pnpm test`; при изменениях в API дополнительно `pnpm test:int`.
- Docker:
  - перед `build`/`up` проверять `df -h /System/Volumes/Data`; если свободно меньше 2 ГБ — BLOCKED;
  - `down` выполнять без `-v`;
  - удалять только висячие образы `carbone-reports`.

## Review Focus

1. **Redis недоступен при старте или во время работы.** Ожидание:
   - API стартует;
   - отчёты формируются (кэш Carbone промахивается);
   - вход работает (лимит пропускается);
   - ни один запрос не висит дольше примерно 0,5 с из-за Redis.

   Проверка: Task 1, Task 2.
2. **Несколько экземпляров API.** Ожидание: лимит входа общий, 11-я попытка за минуту с любого экземпляра даёт 429. Проверка: Task 2, интеграционный тест с двумя приложениями на одном Redis.
3. **Медленный SQL плюс медленный Carbone.** Ожидание: суммарно не дольше `REPORT_TIMEOUT_MS` (с небольшим допуском), ответ 504, запуск в истории со статусом error. Проверка: Task 3.
4. **Пользователь быстро печатает в родительском текстовом поле.** Ожидание: один запрос вариантов после паузы, без «мигания» сброса дочернего значения на промежуточных значениях. Проверка: Task 4.
5. **Зависший `pg_dump`.** Ожидание: через `BACKUP_TIMEOUT` процесс прерывается, блокировка снимается, остаётся `.partial`. Проверка: Task 5.

- [ ] **Step 3: Реализация**

`redis.ts`:
```ts
import { Redis } from 'ioredis';

export function createRedis(url: string, log: { warn(o: object, m: string): void }): Redis {
  const redis = new Redis(url, {
    maxRetriesPerRequest: 1,
    enableOfflineQueue: false,
    connectTimeout: 2000,
    commandTimeout: 500,
  });
  let lastLog = 0;
  redis.on('error', (err) => {
    const now = Date.now();
    if (now - lastLog > 30_000) {
      lastLog = now;
      log.warn({ err: err.message }, 'Redis недоступен — кэш и лимит входа работают без него');
    }
  });
  return redis;
}
```
`template-cache.ts`: две реализации по интерфейсу. Префикс ключа `cr:carbone:tpl:`, срок жизни 604800.

`client.ts`: вместо `Map` использовать `this.cache.get` и `this.cache.set`. После успешной загрузки — `await cache.set(...)`. Ошибки кэша не должны превращаться в ошибки рендера.

`server.ts`:
```ts

new CarboneClient({ baseUrl, cache: redisTemplateCache(redis) });
```

- [ ] **Step 1: Тесты**

- `deadline.test.ts` на фейковых часах:
  - `remaining`;
  - `cap`;
  - `check` после истечения → `AppError` TIMEOUT 504 с точным текстом;
  - `race` с долгим промисом → TIMEOUT.
- `reports.int.test.ts`. Отдельное приложение с `reportTimeoutMs: 800` (через переопределение конфига в `createTestApp`; добавьте такую возможность, если её нет) и поддельным Carbone, который ждёт 2 с:
  - `POST render` → 504 «превышено время формирования отчёта» быстрее 1,5 с;
  - в `/api/runs` появился запуск со статусом error и этим текстом (Review Focus 3).
- Второй случай: SQL `select pg_sleep(2)` при `queryTimeoutMs: 30000` и `reportTimeoutMs: 800` → 504 до 1,5 с.

- [ ] **Step 2: Реализация**

`render` и `preview` создают `new Deadline(config.reportTimeoutMs)` в начале обработки и передают его дальше:
- SQL получает `timeoutMs: deadline.cap(config.queryTimeoutMs)`, и для запросов отчёта, и для вариантов параметров;
- Carbone получает `timeoutMs: deadline.cap(config.renderTimeoutMs)`;
- весь сбор и рендер обёрнуты в `deadline.race(...)`, чтобы срок соблюдался даже там, где таймаут не передаётся.

Ошибка таймаута SQL (`statement_timeout`) при исчерпанном сроке должна выдаваться как TIMEOUT 504 с текстом срока отчёта, а не как SQL_ERROR. Если после ошибки SQL `deadline.remaining() <= 0`, бросайте TIMEOUT.

### Task 4: Форма отчёта и история

**Files:**
- Modify:
  - `apps/web/src/components/ParamForm.tsx` и тест
  - `apps/web/src/pages/ReportRunPage.tsx` и тест
  - `apps/web/src/lib/format.ts` (или место, где форматируются параметры истории)
  - `apps/web/src/pages/HistoryPage.tsx` и тест

**Interfaces:**
- Produces: `ParamForm` получает необязательный проп `onOptionsLoadingChange?: (loading: boolean) => void`. Он вызывается, когда меняется «загружается ли хоть один SQL-параметр».

- [ ] **Step 1: Тесты (RED)**

1. **Debounce.** У `city` есть родитель `prefix` — текстовый параметр. Набор «abc» с `userEvent` на фейковых таймерах (`vi.useFakeTimers({ shouldAdvanceTime: true })`) → до 400 мс запросов `options` нет, после — ровно один с `prefix: 'abc'`. Дочернее значение не сбрасывается на промежуточных значениях (Review Focus 4).
2. **Кнопка.** В `ReportRunPage` при SQL-параметре, чей `options` ещё не ответил (handler с задержкой), «Сформировать» неактивна и рядом виден текст «Загружаются варианты параметров…». После ответа кнопка активна.
3. **История.** Параметры `{ ids: [1, 2], from: '2026-01-01' }` показываются как `ids: «1, 2», from: 2026-01-01`. Существующий формат одиночных значений не меняется.

- [ ] **Step 2: Реализация**

- **Debounce.** `useDebouncedValue(parentParams, 400)` — хук на `useState` и `useEffect` с `setTimeout`. Применяется только если среди родителей есть параметр типа `string` или `number`; для остальных значение используется сразу. Ключ запроса строится из отложенного значения. Пока отложенное значение отличается от текущего, поле считается загружающимся.
- **Загрузка.** `QueryParamField` сообщает наверх `isFetching || pendingDebounce`. `ParamForm` агрегирует по всем полям и вызывает `onOptionsLoadingChange` при изменении. `ReportRunPage` хранит флаг, блокирует кнопку и показывает текст.
- **История.** Форматирование массива: `«${arr.join(', ')}»`.
